# 페르소나별 자연어 질문 생성기 예시

형태: LLM에 복사해 사용할 질문 생성 프롬프트와 가상 출력 예시.

목적은 사용자가 정확한 도감 용어를 몰라도 입력할 법한 질문을 모으는 것이다. 질문 생성과 정답·근거 검수는 분리한다. 생성한 문장은 실제 사용자 조사 결과가 아니며, 이 기획 문서는 서비스 검색 색인에 넣지 않는다.

이 문서는 **같은 정보 요구 3개를 P1·P2·P3 세 페르소나의 표현으로 만드는 통제 예시**다. 각 유형별 3개씩 총 9표현을 만들되, 공통 정보 요구는 I01~I03 세 개로 유지한다.

여기의 9표현은 [problem.md 5절](problem.md#5-사용자별-네이티브-질문답변검증-카드-9개)의 **P1-01~P3-03 검수 카드 9개와 다른 세트**다. 검수 카드는 실제 여정에서 서로 다른 개념·비교·조건 변경 질문을 다루며, 이를 같은 정답으로 묶지 않는다. 상세 페르소나와 공통/개별 여정의 기준은 [problem.md](problem.md)를 따른다.

## 1. 입력할 공통 상황

- 게임: 1세대 Red/Blue. 싱글 배틀을 준비하며 도감을 찾는다.
- 이번 가상 상황에서는 상대가 롱스톤이라고 미리 주어진다.
- 후보: 파이리·꼬부기·피카츄, 모두 레벨 20.
- 현재 기술: 파이리의 불꽃세례·할퀴기, 꼬부기의 물대포·몸통박치기, 피카츄의 전기쇼크·전광석화.
- 피카츄는 현재 10만볼트를 보유하지 않았다.
- 상태 이상·능력 변화 없이 기본 타입을 유지하며, 남은 PP는 충분하다.
- I02의 비교 기준은 제공된 현재 공격 기술의 기본 타입 상성이다. 실제 피해·생존·상대 행동·승률까지 판정하는 질문으로 확장하지 않는다.

이것은 기획용 보유 목록이다. 게임을 처음 시작하면 자동으로 주어지는 목록을 뜻하지 않는다. 실제 입력에 상황이 없으면 생성기가 임의로 채우지 않는다.

## 2. 페르소나와 정보 요구

| 대상 | 배경·알고 있는 것 | 질문 표현의 설계 가설 |
| --- | --- | --- |
| P1: 8세 남아, 1세대 실전 초보자 | 최신 애니메이션과 포켓몬 책에 관심이 높고 이름·기술명이 친숙함. 게임 조작에 익숙하지만 1세대 실전은 처음이며, ‘상성’ 같은 용어를 안다고 가정하지 않음 | ‘누가 쎄?’처럼 반말로 현재 선택·다음 행동을 직접 묻는 일상 질문·검색체. 도감 용어나 맞춤법으로 강제 교정하지 않음 |
| P2: 30대 여성 입문자 | 스토리와 피카츄는 친숙하지만 전략·타입 상성의 기초는 낯섦 | 존댓말 없이 짧게 상황을 적고 시작점·선택 이유·준비 방법을 묻는 질문·검색체 |
| P3: 20대 남성 숙련자 | 게임·대전 경험이 있고 상성·자속·종족치·기술 구성에 익숙함. Red/Blue의 모든 예외를 안다고 가정하지 않음 | 전문 용어를 쓸 수 있으며 ‘뭐함?’, ‘어떻게함?’, ‘됨?’, ‘그대로감?’처럼 짧은 구어체로 조건·전제·근거를 확인 |

나이·성별은 이 문서의 가상 프로필이다. 지식 수준과 말투는 별도 설계 항목이며 나이·성별에서 추정하지 않는다. P1에게 유아체를 붙이거나 P2에게 존댓말을 붙이지 않으며, P3의 문장을 명사형으로만 제한하지 않는다. 같은 정보 요구의 대상·관계·조건은 유지한다.

‘쎄?’를 무조건 ‘상성’으로 치환하지 않는다. 이 통제 예시에서는 공통 상황에 주어진 비교 기준 안에서 읽으며, 실제 입력에 비교 기준이 없으면 무엇을 비교하려는지 확인한다. 기본 정보나 습득 방법을 묻는 질문에 ‘쎄?’를 억지로 추가하지 않는다.

| 정보 요구 ID | 확인하려는 정보 |
| --- | --- |
| I01 | 롱스톤이 어떤 포켓몬인지 기본 정보 확인 |
| I02 | 주어진 후보와 현재 기술로 롱스톤을 상대할 준비 선택 |
| I03 | 피카츄가 10만볼트를 배우는 방법 확인 |

## 3. 복사해 사용할 생성 프롬프트

~~~text
당신은 포켓몬 게임 초보자와 숙련자의 자연스러운 질문 후보를 만드는 기획 보조자다.

[공통 상황]
게임은 1세대 Red/Blue이며 싱글 배틀 전 도감을 찾아본다.
상대는 롱스톤으로 주어졌다.
후보는 레벨 20의 파이리·꼬부기·피카츄다.
현재 기술은 파이리: 불꽃세례·할퀴기,
꼬부기: 물대포·몸통박치기, 피카츄: 전기쇼크·전광석화다.
피카츄는 10만볼트를 보유하지 않았다.
상태 이상·능력 변화 없이 기본 타입을 유지하며, 남은 PP는 충분하다.
후보 선택은 제공된 현재 공격 기술의 기본 타입 상성을 비교하는 범위다.

[페르소나]
P1. 8세 남아. 최신 애니메이션과 포켓몬 책에 관심이 높고 이름·기술명이 친숙하다.
    게임 조작에는 익숙하지만 1세대 실전은 처음이다. '상성' 같은 용어를 안다고 가정하지 않는다.
    '누가 쎄?'처럼 반말로 지금 선택할 것과 다음 행동을 직접 묻는 일상 질문·검색체를 쓴다.
    '쎄?' 같은 구어체를 도감 용어나 맞춤법으로 강제 교정하지 않는다.
P2. 30대 여성 입문자. 스토리와 피카츄는 친숙하지만 전략·타입 상성의 기초는 낯설다.
    존댓말 없이 상황과 궁금한 점을 짧게 적는 질문·검색체를 쓴다.
P3. 20대 남성 숙련자. 게임·대전 경험이 있고 상성·자속·종족치·기술 구성에 익숙하다.
    전문 용어를 쓸 수 있지만 질문은 '뭐함?', '어떻게함?', '됨?', '그대로감?'처럼 짧은 구어체로 쓴다.
    적용 버전·비교 또는 계산 전제·근거를 확인하되 명사형으로만 끝내지 않는다.
나이·성별은 가상 프로필이며 지식·감정·성격·말투를 결정하는 근거로 쓰지 않는다.
위에 따로 명시한 지식 수준과 말투를 적용하며, 예시 어미를 고정 유행어처럼 반복하지 않는다.

[정보 요구]
I01: 롱스톤의 기본 정보가 궁금하다.
I02: 후보와 현재 기술 중 이번 상대에게 준비할 선택이 궁금하다.
I03: 피카츄의 10만볼트 습득 방법이 궁금하다.

[작성 규칙]
1. P1·P2·P3 각각 I01~I03 질문을 하나씩, 총 9개 작성한다.
2. 같은 ID의 질문은 대상·관계·조건·원하는 정보를 유지한다.
3. 설정한 일상 질문·검색체를 사용한다. P1에게 전문 용어 사용을 요구하지 않고 P2 질문에는 존댓말을 쓰지 않는다. P3는 전문 용어와 짧은 구어체를 함께 쓸 수 있다. 나이·성별에 따른 유아체·과장된 말투·성별 밈은 넣지 않는다.
4. 공통 상황에 없는 보유 기술·상대·버전·취향·진행 상태를 만들지 않는다.
5. 정답·상성 배율·예상 수치·허용 근거는 입력받거나 출력하지 않는다.
6. 빠진 사용자 입력은 몰래 채우지 말고 '추가 입력'에 표시한다.
7. 자료로 답하기 어려운 질문도 억지로 검색 용어에 맞춰 고치지 않는다.
8. 표현만 다른 질문을 서로 다른 정보 요구라고 계산하지 않는다.
9. P3의 버전·전제·근거 확인은 같은 정보 요구의 적용 기준을 명료하게 하는 표현이다.
   배율·실제 피해·승률의 별도 산출이나 다른 버전 비교 등 새 과제를 끼워 넣지 않는다.
10. 현재 기술 제외·상대 변경 같은 추가 조건 사례는 이번 9개에 섞지 않고 별도로 제안한다.
11. 사용자 입력 부족과 원문 근거 부재를 구분한다. 생성 단계에서는 원문을 검수한 척하지 않는다.
12. '쎄?'를 무조건 '상성'으로 치환하지 않는다. 공통 상황에 비교 기준이 있으면 그 범위에서 사용하고, 없으면 비교하려는 의미를 확인할 필요가 있음을 표시한다. I01의 기본 정보·I03의 습득 방법 질문에는 '쎄?'를 억지로 넣지 않는다.

[출력]
표로 작성한다.
열: 페르소나 / 정보 요구 ID / 자연어 질문 / 사용한 상황 정보 / 추가 입력 / 근거 검수
추가 입력은 실제로 빠진 사용자 조건만 적고, 없으면 '없음'으로 적는다.
근거 검수는 '미검수'로 표시한다. 답변 가능 여부·정답·출처의 확정은 이후 원문 검수 단계로 남긴다.
이 출력은 기획용 질문 후보이며 공식 평가셋 파일이나 정답표가 아니다.
~~~

9개 표현이지만 공통 정보 요구는 3개다. 같은 사실의 표현 변형으로 공식 평가의 고유 문항 수를 늘리지 않는다. problem.md의 9개 검수 카드와 이 표를 합쳐 고유 문항 18개를 확보했다고 세지 않는다.

### 맥락·자료 부족과 조건 변경을 점검하는 별도 사례

| 입력 | 사용자 입력 확인 | 원문 검수·이번 통제 예시와의 관계 |
| --- | --- | --- |
| 얘한테 뭘 써? | 현재 세션에서 얘가 누구인지 명확한가? 모호하면 대상만 확인 | 입력 부족을 곧바로 원문 근거 부재로 판정하지 않음 |

이 별도 사례의 개수는 위 9표현에 포함하지 않는다. 입력이 부족하면 필요한 조건을 확인하고, 조건이 충분한데 원문이 답을 뒷받침하지 못하면 근거 보강·정보 부족 안내 대상으로 구분한다.

## 5. 생성 뒤 팀이 할 검수

P1-02 검수 카드의 승인된 입력은 **“물대포랑 몸통박치기 뭐가 더 쎄? 둘 다 얼마나 쎄고 얼마나 잘 맞아?”**다. 두 기술 비교·센 정도·잘 맞는 정도를 묻는 의도를 유지한다. 질문에 ‘위력·명중률’을 직접 넣거나 괄호로 풀이하고 ‘숫자도’라고 덧붙이지 않는다. 이 예시는 `problem.md`의 P1-02이며, 위 I01~I03 통제 예시 9개에 새 문항으로 합산하지 않는다. 다른 8개 검수 카드의 질문은 이번 수정에서 유지한다.

1. 같은 ID의 세 질문이 실제로 같은 대상·조건·정보를 요구하는지 먼저 확인하고, 표현·설명 수준의 차이는 따로 검토한다.
2. 현재 자료로 답할 수 있는지, 사용자 입력이 필요한지, 원문 보강이 필요한지 구분한다.
3. 사용자(팀원)가 채택한 질문의 필수 정답·원문 위치·허용 대안·오답 기준을 검수한다. 이 문서의 생성 프롬프트에 그 정답·허용 근거를 되돌려 넣지 않는다.
4. 자연어 질문을 정확한 검색어로 사용자에게 다시 쓰게 하지 말고, Agent가 이름·맥락·관계를 연결하는지 점검한다.
5. 고정한 최종 평가 문항을 성능에 맞춰 다시 생성·수정하지 않는다.
6. 추천 성공·허용 후보·우선순위는 팀 논의가 필요한 사항이다. 질문 생성만으로 정답이나 성공 기준이 확정됐다고 기록하지 않는다.

이 문서는 질문 생성 예시다. 서비스의 자동 생성 기능이나 사용자 학습 효과가 구현·검증됐다는 의미는 아니다. 프로젝트 범위와 성공 기준은 [problem.md](problem.md)를 따른다.

## 6. 질문 후보 생성 역할과 평가셋의 연결

기획용 질문 후보를 만드는 역할은 [question-designer 에이전트](../.claude/agents/question-designer.md)와 [question-design 스킬](../.claude/skills/question-design/SKILL.md)의 설계에 연결한다. 이 문서의 예시가 해당 Agent의 구현·실행 완료를 뜻하지는 않는다.

후보 제안 → 사용자(팀원)의 채택·원문 검수 → 공식 평가셋 작성·잠금 → 평가 실행·사람 채점의 단계를 구분한다. [현 평가셋 소유 규칙](../eval/README.md)에 따라 공식 평가셋과 잠금은 사용자만 작성·수정한다. 질문 생성 역할이 정답표·최종 평가셋을 읽어 후보를 맞추거나 공식 평가 파일을 자동 생성·수정하지 않는다.
