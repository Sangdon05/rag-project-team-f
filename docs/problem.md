# 포켓몬 도감 RAG — 문제·사용자·탐색 여정·평가 기준

포켓몬스터 1세대 게임의 초보자와 숙련자가 **싱글 배틀을 준비하며 도감을 찾아보는 순간**에 개입한다. 사용자가 자연스럽게 질문하면 필요한 도감 정보를 찾고, 주어진 후보와 현재 기술의 기본 상성을 비교하여 **어떤 선택을 준비할지와 그 이유**를 근거와 함께 설명한다.

이 문서는 사용자 정의·탐색 여정·네이티브 질문·답변 예시·근거·검증을 연결하는 공유 문서다.

> 최신화: 2026-11-25, 팀 main 26ee61b 기준. **추천 성공 기준과 공식 평가 경로는 미정 — 팀 합의 필요**다. 허용 후보·우선순위·합격 목표를 임의로 확정하지 않는다. 9개 카드는 검토 후보이며 확정된 개발·최종 평가셋이나 실제 RAG 실행 결과가 아니다.

## 1. 문제와 서비스의 개입 범위

| 항목 | 정의 |
| --- | --- |
| 프로젝트 주제 | 포켓몬 도감을 구성하여 상대 포켓몬의 상성에 맞는 포켓몬 추천 및 전략 설명 |
| 대상 게임·데이터 | 현재 팀 기준인 **1세대 Red/Blue**, 포켓몬 151종·기술 165개·타입 15개 |
| 공통 이용 상황 | 초보자(P1·P2)와 숙련자(P3)가 **싱글 배틀 전에 도감을 찾아보는 상황**. 한 번에 한 포켓몬을 내보내는 배틀을 전제로 하며, 더블 배틀의 동료·범위 기술 조합은 다루지 않음 |
| 진입점 | 이름·특징·기술·상성 등 궁금한 내용을 자유롭게 질문하거나, 비교할 후보를 입력하는 순간 |
| 완료 지점 | 확인된 조건에서 필요한 도감 사실을 이해하고, 비교 질문이라면 준비할 후보·기술과 선택 이유를 확인한 순간 |
| 현재 추천의 뜻 | 사용자가 제시한 후보와 현재 기술의 **기본 공격 상성**을 비교한 조건부 추천. 상대 행동까지 포함한 전체 배틀 최적 전략은 아님 |
| 제외 | 1세대 이후 정보, 더블 배틀, 실제 플레이 조작, 실시간 게임 상태 추적, 승률 계산·필승 보장 |

표의 완료 지점은 서비스 개입 범위의 설계이며 추천 성공 판정의 합의를 뜻하지 않는다.

상대 포켓몬을 이미 아는 것은 모든 질문의 선행 조건이 아니다. “롱스톤이 뭐야?”에는 기본 정보만 조회한다. “이 셋 중 누구를 준비해?”처럼 상대에 따라 답이 달라지는 질문에만 상대·후보·현재 기술 등 필요한 조건을 확인한다.

### 이 범위를 정한 근거

| 근거 | 문서에 반영한 내용 |
| --- | --- |

| 프로젝트 발제 STEP 1·2 | 사용자·기존 탐색·질문 범위·오답 위험·RAG 이유·제외 범위 정의, 질문–정답–근거 연결 |

세 페르소나, 안내 순서, 후속 질문 버튼은 팀의 서비스 설계다. 발제에서 특정 페르소나나 화면 형식을 지정한 것은 아니다.

### RAG를 선택하는 이유

초보자의 일상 표현을 도감 항목과 설명 원문에 연결하고, 버전·습득 조건처럼 혼동하기 쉬운 내용을 찾아 **선택 이유와 확인 가능한 출처**를 함께 제공하기 위해서다. 이름·수치 조회와 상성 계산은 정확한 데이터·규칙을 사용하고, 개념·조건·설명은 수록된 원문을 검색한다. 이 조합의 검색 정확성과 답변 신뢰성을 질문–정답–근거 평가로 검증한다.

## 2. 사용자 페르소나

P1·P2는 실제 1세대 게임의 초보자이며 P3는 포켓몬 게임·대전 경험이 있는 숙련자다. 모두 싱글 배틀 전 도감을 찾아본다. **P3 추가 후에도 P1·P2의 입문 여정은 유지한다.** 아래는 팀이 설정한 페르소나이며 실제 사용자 조사 결과는 아니다. 나이·성별로 지식과 말투를 추정하지 않고, 각 캐릭터에 명시된 관심·경험·정보 요구·입력 방식을 따른다.

| 항목 | P1 — 관심이 높은 8세 게임 초보자 | P2 — 30대 입문자 | P3 — 20대 숙련 플레이어 |
| --- | --- | --- | --- |
| 연령·성별 | 8세 남아 | 30대 여성 | 20대 남성 |
| 포켓몬과의 접점 | 최신 애니메이션·포켓몬 책에 관심이 매우 높고 이름·기술명이 친숙함. 1세대 정보는 불명확할 수 있음 | 과거 스토리와 피카츄·파이리 등 일부 캐릭터에 익숙 | 게임·대전 경험과 도감·기술 정보 탐색 경험 |
| 게임 경험 | 다른 게임 조작·선택 구조에 익숙하나 실제 1세대 게임은 처음 | 캔디크러시 등 단순 모바일 게임에 익숙하며 전략 게임 경험은 적음 | 팀 구성·기술 선택 경험이 있음. Red/Blue의 모든 예외까지 안다고 가정하지 않음 |
| 이미 아는 것 | 포켓몬 이름·기술명이 친숙함. ‘상성’ 등 전문어의 의미를 이해하는지는 확인되지 않음 | 스토리와 일부 캐릭터 | 상성·자속·종족치·기술 구성 |
| 어려운 것 | 게임 실전에서 후보·기술을 고르는 것. 익숙한 이름과 전문어 이해를 구분할 필요가 있음 | 무엇부터 검색할지, 위력·PP 등 항목의 의미 | 버전별 차이·계산 전제·현재 기술 변경·지원 한계 구분 |
| 이용 동기 | 게임을 빠르게 익히고 유리한 선택 준비 | 방대한 도감 대신 지금 필요한 정보와 선택 확인 | 조건·근거를 빠르게 대조하고 잘못된 전제 검토 |
| 검색 입력 방식 | 친숙한 이름·기술명을 넣어 “쎄?”처럼 짧은 일상 반말로 질문. 원표현을 유지하고 맞춤법·전문어로 다시 쓰게 하지 않음. 전문어를 자연스럽게 쓴다고 가정하지 않음 | 존댓말 없는 짧은 상황 질문·검색체. 모르는 용어와 다음 행동을 바로 질문 | 용어는 알지만 “뭐함? 어떻게 함? 됨? 그대로 가도 됨?”처럼 짧은 구어체·검색체로 질문 |
| 첫 질문 예시 | “롱스톤한테 전기쇼크가 쎄? 전광석화가 쎄?” | “피카츄밖에 모르는데 뭐부터 봐?” | “물대포 타입 배율이랑 자속 각각 어떻게 됨?” |
| 필요한 도움 | 익숙한 기술명을 실제 선택과 연결하고, 필요한 전문어는 쉽게 풀이. 습득 가능과 현재 보유 구분 | 시작점·필요한 용어·짧은 이유와 다음 행동 | 계수 분리·조건 갱신·버전·원문 위치·미지원 범위 |
| 답변 방식 | 비교표와 핵심 조건 먼저 | 짧은 결론과 필요한 설명을 순서대로 | 입력·버전·계수 표와 근거·한계를 간결하게 |
| 도달 목표 | 주어진 사실을 선택에 적용하도록 지원 | 필요한 항목과 선택 이유를 확인하도록 지원 | 적용 전제와 계산의 타당성을 검토하도록 지원 |

같은 질문·조건이면 사실·규칙·근거는 동일하다. 다른 정보 요구에는 별도 검수 기준을 쓴다. “PP의 뜻”과 “기본 PP 숫자”를 같은 정답으로 묶지 않는다. 나이나 성별·페르소나별로 질문 순서를 강제하지 않는다. 포켓몬에 대한 높은 관심이나 이름·기술명 친숙도가 전문어·전략 이해를 증명하지는 않는다. 검색 입력의 짧은 말투와 시스템의 답변 방식도 별도로 설계한다.

## 3. 공통 탐색 과정과 안내 구조

### 기존 탐색의 어려움

사용자는 도감 사이트에서 이름·번호·타입을 검색하고, 여러 포켓몬·기술 페이지를 오가며 정보를 비교한다. P1은 사실을 현재 선택에 적용하는 데, P2는 검색할 항목과 용어를 알아내는 데 어려움을 겪는다. P3는 조건·버전·계산 한계를 대조하는 데 시간이 든다. 세 유형 모두 버전별 수치·습득 조건을 섞을 위험이 있다.

### 화면을 만들 때 참고할 공통 단계

| 단계 | 사용자 행동 | 화면에서 보여줄 내용 | 백엔드가 유지·확인할 정보 |

| 4. 결과 확인 | 사실·비교·설명을 읽고 근거 열기 | 결론, 비교표, 쉬운 설명, Red/Blue 기준과 출처. 미확인 항목은 별도 안내 | 조회 결과·계산 결과·실제 검색 청크·부족한 근거·오류 상태 |
| 5. 선택·후속 탐색 | 준비할 후보·기술을 정하거나 다른 질문 | “다른 후보 비교”, “기술 정보 보기”, “습득 방법 보기” 등 현재 지원 범위의 후속 동작 | 선택 결과와 조건 유지. 후속 질문이 바뀌면 필요한 도구를 다시 선택 |

기술 습득표를 현재 보유 기술 목록으로 자동 채우지 않는다. 현재 기술은 사용자 입력·확인을 받는다. 그림·외형 검색, 포획 장소 안내는 해당 자료와 기능이 확인된 뒤에 제공한다. 일반 결과 화면에는 사람이 읽을 수 있는 출처를 보여주고, 원시 필드·실행 기록은 검증 화면에서 확인한다.

안내 수준 선택 이름은 **“짧게 안내” / “비교 자세히”**로 두는 설계안이다. 기본값은 “짧게 안내”이며 누구나 결과 화면에서 변경할 수 있다. 변경 시 버전·입력 후보·현재 기술·계산 사실은 유지하고 설명의 순서와 펼침 정도만 바꾼다. 회원가입 때 나이별 서비스 유형을 선택하게 할 필요는 없다.

    A2 --> A3[선택 이유와 다른 기술 습득 확인]
    P2 --> B1[이름과 무엇을 볼지 질문]
    B1 --> B2[필요한 용어·정보부터 확인]
    B2 --> B3[내 후보와 현재 기술을 연결해 비교]
    A3 --> R[같은 사실·같은 규칙·같은 출처]
    B3 --> R
    R --> E[조건부 선택과 이유 확인]
~~~

| 여정 | P1 — 적용·비교 | P2 — 시작점·이해 | P3 — 조건·근거 검토 |
| --- | --- | --- | --- |
| 시작 | 기술이 상대에게 통하는지 질문 | 무엇을 먼저 찾아야 하는지 질문 | 버전·현재 기술·비교 전제 입력 |
| 정보 확인 | 상대 타입과 기술 수치 비교 | 기본 정보·필요한 개념 확인 | 타입 배율·자속·결합계수 구분 |
| 조건 연결 | 현재 기술에서 선택지를 좁힘 | 내 후보·기술을 비교로 연결 | 변경한 현재 기술로 판단 재검토 |
| 추가 탐색 | 다른 기술의 습득 방법 | 다음 행동에 필요한 정보 | 미지원 계산과 원문 위치 |
| 도착 | 선택 근거 확인 | 필요한 정보와 선택 이유 확인 | 적용 조건·계산·한계의 타당성 검토 |


이 순서를 강제하는 설문형 흐름은 아니다. P2도 바로 비교를 질문할 수 있고 P1도 용어 설명을 요청할 수 있다. 학습·관심 수준이 달라도 같은 계산 결과를 바꾸지 않는다.

### API + 웹 자료를 연결하는 방식

팀원이 API와 웹 자료를 합성·보강 중이라는 공유와 실제 서빙 완료는 구분한다. API 사실, 웹 원문, 편집한 설명, 규칙 계산 결과를 구별해 저장한다. 각 문서에는 문서 ID·제목·원본 URL·이용 조건·게임 버전 또는 수집 시점·원문 절/행을 남기고, 편집본은 원문으로 거슬러 올라갈 수 있게 한다.

검색을 위해 JSON의 사실을 문장·표로 렌더링할 수는 있다. 이때도 id + 필드 + 버전 위치를 보존하고 원문에 없는 전략을 만들어 넣지 않는다. 평가용 질문·정답표와 이 문서의 예시 답변은 검색 코퍼스에 넣지 않는다. 서로 다른 세대·배틀 형식의 공략은 Red/Blue 근거로 합치지 않는다.

최신 팀 청킹 설계는 포켓몬별 Markdown을 주제별로 나누고 원본 근거를 연결하는 방식이다. 추가 데이터 파일의 존재만으로 청크 생성 완료를 선언하지 않는다. 정확 습득 조회는 E04와 검수한 머신 매핑을 사용한다. 개념 설명도 원문·섹션·메타데이터 연결이 필요하다.

| 기본 상성 계산 | E05 코드·기본 배율 확인 내용 | 실제 피해·KO 타수·승률 |
| 이상해씨 청킹 파일럿 | [생성기](../scripts/helper/build_pilot_chunks.py), [v3a 문서](../data/synthetic/pilot/v3a/bulbasaur_red_blue.md)와 [청크 JSON](../data/synthetic/pilot/v3a/bulbasaur_red_blue.json)의 10개 청크 | 151종 전체 문서·청크 생성 |
| 파일럿 벡터 검색 | [색인·검색 코드](../scripts/helper/pilot_vector_index.py), [저장된 v3a 원본 기록](../results/pilot/smoke_v3a.json): 10행·27질의·오류 0 | 이번 문서 반영에서 모델·DB는 재실행하지 않음. 서비스 도구 8개·전체 답변 체인·API 완료와 다름 |
| 검색 방식·공식 평가 | A/B/C·C+RW 설계와 평가 운영 명세 | BM25·RRF·reranker 구현 및 공식 고정 평가 실행 완료 |

현재 채택된 파일럿 템플릿은 **tpl3a**, tpl3b는 기각된 실험이다. 최신 파일럿 사본과 버전별 기록을 구분한다. 정적 산출물·저장된 실행 기록 확인과 현재 환경의 실제 서비스 실행 성공은 다른 상태다.

네이티브 질문은 검색 입력이고 원문 청크와 다르다. 질문 이해·리라이트·질의 임베딩은 원문 청킹과 구분한다. 평가용 질문·정답표·이 문서 자체를 서비스 검색 색인에 넣지 않는다.


## 7. 자연어 이해와 RAG 도구 선택

### 원칙: 질문을 사용자에게 검색어로 고쳐 쓰게 하지 않는다

서비스는 원질문을 유지하면서 **무엇을 묻는지 / 누구·어떤 기술인지 / 어떤 관계인지 / 적용 버전·현재 조건이 무엇인지**를 파악한다. 같은 단어라도 “물대포 몇 번?”은 PP 조회, “물대포 배워?”는 습득 조회, “물대포 통해?”는 상대를 포함한 상성 판단이다.

| 자연어 입력 | 해석·확인 | 선택 경로 |
| --- | --- | --- |
| “롱스톤이 뭐야?” | 포켓몬 기본 정보, 대상 #95 | 이름 해석 → 정확 조회. 상대·후보 설정은 생략 |
| “이 공격 몇 번 써?” | 이전 대화에서 기술이 확정됐는지 확인. 기본 PP인지 현재 남은 PP인지 구분 | 확정된 기술 조회. 현재 PP가 필요하지만 입력이 없으면 해당 값만 확인 |
| “얘한테 전기 써도 돼?” | 얘의 대상과 전기가 타입인지 특정 기술인지 확인 | 맥락에 없는 대상·기술을 임의 채우지 않음. 타입 관계만 묻는 경우 전체 배틀 조건까지 요구하지 않음 |
| “10만볼트 레벨 올리면 돼?” | 기술 #85, 포켓몬·버전 확인, 레벨업 여부를 묻는 관계 | 습득표 조회. 질문의 전제를 사실로 받아들이지 않음 |

리라이트는 검색에 필요한 질의를 명료하게 만드는 단계다. “몇 번”을 “기본 PP”에 연결하되, 현재 남은 PP에 대한 질문을 기본 PP 질문으로 바꾸면 의미 보존 실패다. 원질문·대화에서 확인된 조건만 사용하고, 변환 오류 시 원질문 검색으로 돌아간다.

이름 정규화·확인된 맥락 전달·인수 검증은 A/B/C에 동일하게 적용한다. **추가 의미 리라이트는 C+Rewrite에서만 적용**하고, 공통 전처리의 효과를 리라이트 개선으로 중복 계산하지 않는다. 원질문에는 없는 정답·상성·습득 조건을 변환 질의에 넣지 않는다.

### 서비스 도구 8개와 현재 구현 상태

아래 도구는 [팀 도구·스킬 개요](references/skills/README.md)에 연결된 **서비스 명세**다. E05 외에 이상해씨 파일럿 청크 생성·벡터 색인·검색 코드와 저장된 기록이 있다. 이를 아래 8개 도구 래퍼·151종 전체 색인·실제 답변 체인·응답 API 완료로 확대하지 않는다.

| 도구 | 사용하는 질문 | 선택 이유·주의 |
| --- | --- | --- |
| resolve_name(name, kind) | 한글·영문 이름을 ID로 연결 | 정확한 대상 결정. 오타·별칭 후보도 명세 범위지만 사전·실행 검증 전에는 지원 완료로 단정하지 않음 |
| get_pokemon(id) | 한 포켓몬의 타입·스탯 등 | 정확 수치는 정규화 데이터에서 조회. 보강 데이터가 없다고 이미 있는 기본 사실까지 막지 않음 |
| get_move(id) | 위력·명중률·기본 PP·타입 | Red/Blue 값 조회. 숫자의 의미·효과 설명 근거는 별도 확인 |
| get_learnset(pokemon_id, move_id?, method?) | 배우는 기술·습득 방법 | 대상·버전·방법을 필터. 현재 보유 기술로 간주하지 않음 |
| type_effectiveness(user, target, move) | 구체적인 기술의 기본 공격 상성 | 기존 BattleRules.calculate를 감쌈. 현재 기술 보유·습득 적법성은 별도로 확인. 실제 피해·승률은 계산하지 않음 |
| filter_pokemon(types, stat, op, value, sort_by, limit) | 조건에 맞는 후보·순위 | 전체 정규화 데이터를 필터·정렬. 검색 상위 결과만 보고 전체 1위라고 답하지 않음 |
| compare_pokemon(ids, fields) | 지정 후보의 타입·종족치 비교 | 동일한 필드를 직접 비교. 여러 기술 배율 계산·정렬을 이 도구가 이미 지원한다고 가정하지 않음 |
| search_pokedex(query, k, entity, pokemon_id, section, types) | 원문 설명·조건·이유 | 실제 코퍼스 검색과 출처 반환. A/B/C는 이 도구 내부 검색 구성을 바꿔 비교하는 설계 |

현 계약의 type_effectiveness는 사용자·상대·기술을 요구한다. “전기 타입이 롱스톤에게 어때?”처럼 타입 관계만 묻는 질문은 공격 타입·방어 타입 직접 조회 계약을 보완해야 한다. 필요한 계약이 없는데 피카츄·10만볼트를 임의로 넣거나 불필요한 보유 포켓몬 입력을 요구하지 않는다.

별도 질문 라우터를 만들기보다 **도구 설명과 시스템 프롬프트로 도구를 선택하고, 구조화한 입력값을 검증**하는 팀 설계를 따른다. 정확 조회·계산·문서 검색은 필요한 만큼 조합하며, 모든 질문에 서비스 도구 8개를 순서대로 호출하지 않는다.

### RAG 검색 구성 — 서비스 설계와 평가 경로 구분

아래 구조도는 조회·계산·검색을 연결하는 서비스 설계다. 공식 평가에 이 도구 선택 구조를 쓸지, 검색 경로를 고정할지는 미정이다.

~~~mermaid
flowchart TD
    U[원질문·확인된 대화 맥락] --> T[LangChain 도구 선택·인자 검증]
    T --> L[도감·기술·습득 정확 조회]
    T --> M[기본 상성 규칙 계산]
    T --> Q[search_pokedex: 설명 원문 검색]
    Q --> A[A: Vector]
    Q --> B[B: BM25와 Vector를 RRF 결합]
    Q --> C[C: B 후보를 별도 reranker로 재정렬]
    A --> E[근거 선택·버전과 원문 위치 확인]
    B --> E
    C --> E
    L --> O[확인된 사실·계산·검색 근거로 답변]
    M --> O
    E --> O
    O --> V[출처·조건·부족한 정보·실행 기록]
~~~

| 구성 요소 | 이 프로젝트의 적용안 | 이유와 검증할 점 |
| --- | --- | --- |
| 연결·도구 호출 | 팀 환경의 Python·LangChain, 구조화된 도구 입력·출력 | 도구 결과와 출처를 보존하며 생성 단계에 연결 |
| A: 의미 검색 | 동일 청크의 임베딩을 PostgreSQL + pgvector에서 검색 | 이상해씨 단일 벡터 검색 파일럿 기록은 있음. 공식 A 구성·전체 서비스 완료와 구분 |
| B: 단어 + 의미 검색 | 같은 청크에 BM25와 Vector 검색 → **RRF** 결합·중복 제거 | 이름·기술명 같은 정확 단어와 일상 표현을 함께 처리. 서로 다른 원점수를 단순 합산하지 않음 |
| C: 재정렬 | B의 후보를 **질의–청크 관련도를 다시 평가하는 별도 reranker**로 재정렬 | 결합 점수 정렬만으로 reranker를 구현했다고 하지 않음. 모델·입력 후보 수·출력 개수를 실행 설정에 기록 |
| 현재 평가 명세의 최적화 | **Query Rewrite**. C와 C+RW 비교 계획 | 발제는 캐시 또는 Rewrite를 허용하지만 현 평가 명세는 Rewrite만 사용. 구현·실험 완료나 개선 입증을 뜻하지 않음 |
| 근거 범위 | 버전·대상·섹션 메타데이터로 범위를 확인하고 제한 | 다른 세대·비슷한 기술·다른 습득 조건의 오검색 방지. 원문에 없는 필터값을 만들어 넣지 않음 |

A/B/C는 실제 요청마다 세 번 답변하는 화면 기능이 아니라 **같은 질문으로 검색 방식을 비교하는 실험 구성**이다. 공통 생성 모델·프롬프트·출력 한도·컨텍스트 제한을 유지한다. 현재 명세만으로 BM25·RRF·reranker가 구현됐다고 보고하지 않는다. 구체적인 reranker 모델은 실행 확인 전이므로 모델명이 확정된 것처럼 적지 않는다.

도구 조회나 계산만 수행한 응답은 해당 근거를 표시한다. 이를 벡터 검색 성공이나 Hit@5 성공으로 바꾸어 기록하지 않는다. 공식 RAG 평가 문항에는 **실제 검색 가능한 원문과 허용 청크**가 있어야 한다. 숫자 조회 사례만 나열해서 RAG 평가 범위가 확보됐다고 처리하지 않는다.

### 공식 평가 경로 — 미정, 팀 합의 필요

대표 사례는 원문 위치가 보존된 청크와 연결해야 한다. 다만 공식 평가에 사용할 경로는 [저장소 후속 확인 사항](proposals/eval-agent-followups.md)에 미결정으로 남아 있으며 본 문서가 한쪽을 확정하지 않는다.

| 선택지 | 평가 구성 | 합의할 내용 |
| --- | --- | --- |
| 고정 검색 경로 | A/B/C 검색을 항상 수행하는 답변 경로 | 평가 시 툴 사용 범위·체인 구현·실행 인터페이스 |
| 도구 선택 Agent | 툴 포함 전체 답변에서 필요할 때 검색 | 검색 미호출의 집계·설명과 공식 비교 방식 |

**공식 평가 경로는 미정이며 추천 성공 기준과 별도로 팀 합의가 필요하다.** 현 eval 명세는 `retrieval_only`(검색 결과 비교)와 `full_answer`(툴 포함 전체 답변)를 별도 run으로 기록하고 기본 60건·C+RW 20건을 `full_answer`로 두지만, 이것을 경로의 최종 합의 완료로 간주하지 않는다.

현 집계 규칙에서 `retrieval.called=false`는 Hit@5=0, 검색 결과 내 청크 인용의 자동 조건=0이다. 검색 미호출 건수를 별도 보고하고 문항을 분모에서 빼지 않는다. 도구 출처가 제품 답변에서 유효할 수 있어도 공식 검색 성과를 대체하지는 않는다.

경로 확정 후 A/B/C의 툴 설정·생성 조건·출력 한도를 동일하게 고정한다. 정답표를 검색·도구 선택·리라이터 입력에 전달하지 않는다.

## 8. 응답과 화면 상태의 계약 예시

아래는 프론트엔드·백엔드를 연결할 설계 예시이며 현재 제공 중인 API 스키마가 아니다.

| 정보 | 화면에서의 의미 | 백엔드에 보존할 것 |
| --- | --- | --- |
| 결론·핵심 사실 | 질문에 대한 짧은 답, 필요하면 후보·기술 비교표 | answer, facts, recommendations |
| 적용 조건 | Red/Blue, 현재 기술 기준 등 | conditions, 입력값의 출처 |
| 출처 | 조회·계산·검색을 구분한 근거 펼치기 | evidence: source kind, 문서/청크 ID, 필드·절·행, 버전 |
| 부족한 정보 | 추가로 필요한 사용자 입력 또는 원문 | missing_context, missing_evidence |
| 다음 질문 | 현재 정보에 이어질 수 있는 선택 | next_actions. 기능·근거가 있는 동작만 제시 |
| 처리 상태 | 정상 답변, 추가 확인, 일부만 답변, 자료 부족, 지원 밖, 오류 | answered / needs_context / partial / no_evidence / unsupported / error |

사용자 조건이 빠진 경우는 needs_context, 자료에 답이 없는 경우는 no_evidence, 계산 방식이 지원 밖이면 unsupported, 검색·모델 호출 실패는 error로 구분한다. 조회 가능한 사실만 답하고 나머지를 확인할 수 없다면 partial이다. 오류를 정상적인 근거 부족 대응으로 숨기지 않는다.

## 9. 오답·근거 부족과 그 영향

| 판정 항목 | 오답·실패의 예 | 사용자에게 생기는 문제 |
| --- | --- | --- |
| 대상·의도 해석 | “얘”를 임의로 롱스톤으로 해석, PP 질문을 습득 질문으로 바꿈 | 다른 대상·정보를 기준으로 선택 |
| 버전 혼합 | Red/Blue 질문에 Yellow 레벨업·현재 타입·현재 기술 수치를 사용 | 틀린 규칙으로 기술·후보를 준비 |
| 조건 왜곡 | 배울 수 있는 기술을 현재 기술로 간주, 기본 PP를 현재 PP로 단정 | 실제로 사용할 수 없는 선택 안내 |
| 계산·해석 | 물대포의 기본 타입 배율을 6이라 표기, 4배 상성을 승률·실제 피해로 설명 | 상성의 의미를 잘못 학습 |
| 미지원 오해 | 특수 방식·호출 기술 계산의 unsupported를 효과 없음으로 설명 | 정상적인 기술을 쓸 수 없다고 오해 |
| 검색·인용 | 실제 반환되지 않은 청크 인용, 링크가 주요 주장을 뒷받침하지 않음 | 근거를 열어도 답을 확인할 수 없음 |
| 근거 없는 단정 | 미확인 획득 위치·외형·필승 조합 생성 | 불필요한 탐색·육성, 초보자의 잘못된 규칙 이해 |
| 운영 실패 | 검색·모델 오류를 “그런 정보가 없습니다”로 안내 | 자료 부재와 장애를 구분할 수 없음 |

정답은 문장 일치가 아니라 **핵심 사실·조건·한계와 근거가 맞는지**로 판정한다. 필요한 사실이 빠졌거나 맞는 사실 옆에 모순·무근거 단정이 붙어도 정답 충족 실패다. 질문이 모호하면 필요한 조건만 묻고, 근거가 없으면 확인된 부분과 부족한 부분을 나눠 안내한다.

## 10. 성공 기준과 평가셋 연결

### 검증할 가설

- **공통 가설:** 초보자의 일상 표현과 숙련자의 조건·예외 질문도 의도·대상·조건을 보존하여 필요한 도감 사실과 원문에 연결할 수 있다.
- **P1 가설:** 포켓몬·기술명에 친숙하지만 실전은 처음인 사용자에게 쉬운 말로 후보·기술 비교와 적용 조건을 제공하면 배틀 준비 선택을 설명하기 쉬워진다.
- **P2 가설:** 기본 개념이 낯선 사용자에게 시작점과 필요한 정보부터 제공하면 같은 선택까지 도달하기 쉬워진다.
- **P3 가설:** 버전·계산 전제·변경 조건·지원 한계를 함께 제공하면 숙련자의 근거 검토를 지원할 수 있다.

추천 성공·허용 후보·우선순위·합격 목표는 팀 논의 필요다. 아래 지표는 발제의 측정 정의이며 추천 성공의 합의된 판정 기준은 아니다.

앞의 가설 중 검색·답변 정확성은 고정 평가로 검증한다. 초보자에서 입문자로의 실제 학습 변화는 별도의 사용자 관찰·선택 이유 확인이 필요하다. 팀의 예시 대화 검수만으로 학습 효과나 탐색 시간 절감률을 입증했다고 주장하지 않는다.

### 품질 우선 지표

| 항목 | 기준 |
| --- | --- |
| 우선순위 | **품질** — 사실 정확성과 근거를 속도·비용보다 우선 |
| Hit@5 | 최종 답변 가능 17문항에서 허용 근거 청크가 상위 5개에 하나 이상이면1, 합계/17. 실패·검색 미호출은0. 필요한 모든 근거의 회수를 뜻하지 않음 |
| 정답 충족 | 핵심 사실·필수 조건이 모두 맞고 모순이 없으면1, 합계/17 |
| 근거 적합 | 검색 결과 내 청크 인용의 자동 조건과 주요 주장 뒷받침의 사람 판단이 모두 충족되면1, 합계/17 |
| 근거 없음 대응 | 근거 없는3문항에서 지어내지 않고 부족함을 안내하면1, 합계/3. 호출 오류와 구분 |
| 호출 성공률 | 정상 완료한 검색·생성·적용한 리라이트 호출 수/전체 호출 시도 수. 상태가 없으면 추정하지 않음 |
| 응답 시간 | 성공 응답의 입력→완료 시간 중앙값·평균·n. 검색·생성·리라이트 시간 포함. 상태 미확인 시 아래 별도 보고 규칙 적용 |

추천 성공·정확도·응답시간의 **합격 목표값은 미정**이다. 공식 고정 평가 결과도 아직 확인되지 않았다. 발제 지표의 정의를 팀의 추천 성공 판정과 혼동하지 않으며, 목표값은 공식 결과를 보기 전에 고정한다.

### 파일럿 결과 — 공식 평가와 분리

[저장된 템플릿 비교](../results/pilot/smoke_scores.json)는 이상해씨 1종·10청크의 벡터 검색 실험이다.

| 템플릿 | 유효 질의 수 | Hit@5 | MRR | 기록상 상태 |
| --- | ---: | ---: | ---: | --- |
| v1 | 25 | 23/25 | 0.623 | 기준선 |
| v2 | 25 | 25/25 | 0.747 | 비교본 |
| v3a | 25 | 25/25 | 0.765 | 채택 |
| v3b | 25 | 24/25 | 0.755 | 기각 |

원본은27질의이며 이 집계는 범위 밖2개를 제외한25질의 기준이다. **공식 최종17/3 평가에 이 제외 방식을 적용하지 않는다.** 이는 청크 템플릿 비교이며 A/B/C 검색 방식 개선·답변 정확도·추천 성공·151종 전체 성능을 입증하지 않는다. 표현 변형도 포함하므로 서로 다른 답변 가능 정보 요구25개 확보의 증거로 세지 않는다. 이번 문서 반영에서는 모델·DB를 재실행하지 않았다.

### 문항 구성과 고정 원칙

| 구분 | 발제 기준 | 현재 계획과 구분 |
| --- | --- | --- |
| 개발용10 | 답변 가능8 + 근거 없음2 | 튜닝용. 개발 지표 분모는8/2 |
| 최종용20 | 직접 검색10 + 표현 변형·유사 조건7 + 근거 없음3 | 개발·튜닝에 사용하지 않고 버전 고정 |
| 기본 비교 | A/B/C × 20 = 60건 | 캐시 비활성화. 공식 경로 합의 후 동일 조건 고정 |
| 현 평가 명세의 최적화 | C+RW × 20건 추가 | C와 품질·악화·지연·실패 비교. 기본60건과 구분 |

발제는 캐시 또는 Rewrite를 허용하지만 **현재 저장소 평가 명세는 Rewrite만 사용하고 캐싱 실험은 하지 않는 규칙**이다. 캐시15건은 발제의 다른 선택지이며 현 실행 계획에 포함하지 않는다. 위 수량은 실행 요건이지 완료 건수가 아니다.

서로 다른 답변 가능 질문25개를 뒷받침하는 문서 범위, 근거 없는5문항, 혼동 가능한 유사·예외 문서 최소2개가 필요하다. 기존9개 카드는 이 요건을 모두 충족한 평가셋이 아니다. 같은 의미의 표현을 고유 정보 요구로 부풀리지 않는다.

### 평가셋 작성 권한·원본 계약·잠금

소유 규칙과 스키마 원본은 [eval/README.md](../eval/README.md)다. 다음은 **현 저장소 평가 명세의 규칙**으로, 발제가 이 소유 방식까지 강제했다는 뜻은 아니다.

- 사용자(팀원)만 평가셋·잠금 파일을 작성·수정하고 `lock`을 실행한다. Agent는 검증·의견서·실행 기록·자동 집계를 담당하며 평가셋·정답·잠금을 만들거나 고치지 않는다.
- `test`는 개발·튜닝에 사용하지 않는다. 개발 담당 Agent는 평가셋 폴더를 읽지 않는다. 실행기는 원질문·승인된 조건만 체인에 전달하며 정답·허용 근거는 평가에 보관한다. 입력·응답 인터페이스는 팀 확인 사항이다.
- 파일 구조는 `version`과 `items`다. 공식 qid는 dev `D01~D10`, test `T01~T20`이며 P1-01~P3-03은 기획 카드 ID다. 사용자 채택 시 연결 관계를 기록한다.
- 문항은 `qid/split/type/question`, 답변 가능 문항의 `key_facts/allowed_evidence`, 필요 시 `subtype/confusable_with/note`를 사용한다. 허용 근거는 `document_id·chunk_id·source_loc`를 연결한다.
- 근거 없음 문항은 `allowed_evidence`를 비우고 `no_evidence_reason`을 기록한다. 사용자 조건 부족과 원문 부재를 같은 유형으로 세지 않는다.
- 사용자 확정 후 [잠금 도구](../scripts/eval/evalset_lock.py)로 평가셋·청크 해시를 고정하고 실행 전 `verify`한다. 실패하면 평가하지 않는다.
- 청크 내용·경계·ID가 바뀌면 근거 매핑·버전을 확인하고 사용자에게 재잠금을 맡긴다. 잠금 label은 파일의 `version`과 일치해야 한다.
- 검토 기준으로 `eval/dev.json`·`eval/test.json`·`eval/LOCK.json`·전체 `data/chunks/chunks.jsonl`은 아직 없다. 명세·도구 도입과 실제 파일 생성·잠금 완료를 구분한다.

기존 운영 문서의 자동 정답 생성·Eval의 평가셋 수정 문구와 새 사용자 소유 규칙의 충돌은 [후속 확인 사항](proposals/eval-agent-followups.md)에 남아 있다. 본 문서는 현 평가 명세를 연결하되 다른 원본들이 모두 정합화됐다고 단정하거나 충돌을 임의로 해결하지 않는다.

### 사람 채점과 근거 적합

현 평가 명세는 판단 지표를 **사람2명이 독립 채점**하고 불일치를 합의해 최종값·이유를 남기도록 한다. Agent는 사람 채점 칸을 채우거나 LLM으로 판정하지 않는다. 2인 채점·LLM 판정 금지는 발제보다 구체적인 저장소 운영 규칙이다.

근거 적합의 자동 조건은 청크 인용이 하나 이상이고 모두 실제 `retrieval.final`에 존재하는지다. 사람은 그 청크가 주요 주장을 뒷받침하는지 판단한다. 두 조건이 모두 맞아야1이다. 포켓몬·기술 ID 등 도구 출처는 별도 기록하며 검색 근거의 자동 조건으로 세지 않는다.

### 실행 기록과 미확인 지표

원질문·변환 질의·도구 인수/결과·검색 후보/점수·결합/재정렬 전후·사용 근거·원본 답변·시간·상태·채점 이유를 기록한다. 구체적인 형식은 [평가 명세 진입점](../eval/README.md)에서 연결된 원본을 따른다. `retrieval_only`와 `full_answer`, 기본·리라이트·재시도·추가 실험 run을 구분한다.

현재 트레이스 예시에 추가 요청된 항목은 계약·구현 확인이 필요하다.

| 추가 확인할 기록 | 미확인일 때 처리 |
| --- | --- |
| 상태 `ok/no_evidence/error/timeout`와 오류 내용 | 호출 성공률·오류·timeout 수는 `unknown`. 오류를 올바른 거절로 세지 않음 |
| Rewrite 원문·변환 질의·fallback·소요시간 | 해당 항목을 `unknown`으로 두고 의도 보존·추가 지연 검증을 완료했다고 하지 않음 |
| 최종 검색 결과 `document_id/source_loc` | 원문·인용 검증 공백 기록. 출처 위치를 추정하지 않음 |
| A 구성의 최종 k 이전 후보 | 검색 누락·순위 실패 구분의 한계 기록 |
| 실행기와 체인의 입력·응답 계약 | 정답·허용 근거가 체인에 들어가지 않도록 팀 합의 후 연결 |

상태가 없으면 성공 응답만의 시간인지 판정할 수 없다. 시간 값이 있는 전체 시도 기준 평균·중앙값·n을 별도 보고하고 **성공 여부 미확인**을 붙인다. 이를 성공 응답 시간으로 바꾸어 표기하지 않는다.

실패는 처음 어긋난 단계와 원본 기록으로 분류한다. 최종 결과를 본 뒤 튜닝한 실험은 분리하고 실패 삭제·좋은 재실행만 선택한 보고를 하지 않는다. 필요한 기록·사람 채점이 빠지면 미확인·채점 대기로 남긴다.

### 팀 합의가 필요한 미정 사항

| 항목 | 현재 상태 | 이 문서가 확정하지 않는 것 |
| --- | --- | --- |
| 추천 성공 기준 | **미정 — 팀 합의 필요** | 허용 후보·동률 처리·우선순위·설명 충족 조건·합격 목표 |
| 공식 평가 경로 | **미정 — 팀 합의 필요** | 고정 검색 체인 또는 도구 선택 Agent 중 어느 경로를 공식 비교할지 |
| 실행 인터페이스·미반영 trace | 확인·정합화 필요 | 해당 필드가 이미 구현·집계 가능한 상태라는 단정 |
| 기존 운영 문서와 새 평가 명세의 충돌 | 원본 동기화 미완료 | 자동 정답 생성·수정 권한이 모두 일치한다는 단정 |

기존 페르소나와9개 질문은 검토 자료로 유지한다. 합의 전 그 예시를 추천 성공의 확정 정답표로 승격하지 않는다.

## 11. 팀 작업과의 연결

2026-11-25 팀 개인 작업 일지의 기록에 맞춰 담당 영역을 구분한다. 기록된 준비를 실행 성공으로 간주하지 않는다.

| 담당 | 일지에서 확인한 작업 | 이 문서와 연결 |
| --- | --- | --- |
| 상돈님 | 평가 자동화·보고서 요소 정의 | 검수 카드·필요 입력·응답 상태 전달. 자동 평가 구현은 기존 담당과 연결 |
| 정기님 | 데이터셋·임베딩 모델 3종 준비 | 필드·버전·원문 위치·추가 자료 제한 확인. 임베딩 구현을 이 문서에서 확정하지 않음 |

새 eval Agent·평가셋 검토/잠금 도구와 이상해씨 파일럿 청킹·검색 산출물이 추가됐다. 이는 기존 역할 기록을 보완하는 구현 현황이며, 전체 서비스·공식 평가 완료를 의미하지 않는다. 문서 반영만으로 평가셋 작성이나 구현 과업을 자동 시작하지 않는다.

기존 개발 10문항 생성 전 준비 범위와 이번 P3 확장을 구분한다. 9개 카드 작성이 개발 10문항 채택·추천 기준 합의·최종 평가 완료를 뜻하지 않는다.
