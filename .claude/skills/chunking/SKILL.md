# chunking

사람이 읽고 검토한 포켓몬별 Markdown 문서를 질문에 맞는 검색 청크로 나누고, 청크와 원본 근거를 연결한다. 대상은 영문 Red·Blue다.

## 데이터 흐름과 범위

```text
정제 JSON + 검증된 계산 결과 → 포켓몬별 Markdown → 주제별 청크 → 검색·임베딩
```

- `data/processed/`의 정제 JSON은 Markdown의 사실 근거이자 정확한 조회·계산을 위한 데이터다. 전체 JSON을 청크 메타데이터나 임베딩 텍스트로 넣지 않는다.
- Markdown은 포켓몬 한 마리당 문서 하나를 작성하고 사람이 읽고 검토한다. 확정된 문서의 경로와 버전은 실행 기록에 남긴다. `data/synthetic/pilot/`은 파일럿이며 자동으로 승인된 전체 데이터셋이 아니다.
- 사람이 읽는 Markdown에 YAML frontmatter, HTML 주석이나 메타데이터를 넣을 필요는 없다. 문서·청크 ID와 출처는 별도 청크 데이터 및 근거 연결 기록으로 관리한다.
- 임베딩하는 것은 청크의 읽을 수 있는 본문이다. JSONL은 청크 텍스트와 메타데이터를 저장하는 형식일 뿐, 정제 JSON 전체를 임베딩한다는 뜻이 아니다.
- 정확한 습득 여부·레벨 조회에는 정제 데이터를 쓰는 `get_learnset` 툴을 사용할 수 있다. 검색 문서의 기술 목록도 완전성과 출처를 검증한다. 집계·정렬·top-N은 벡터 검색으로 처리하지 않는다.
- 일반 청크 계약과 별도 기술 문서의 범위는 미정이다. Solar 전달본의 포켓몬 문서·청크는 아래 별도 절을 따른다.

### Solar 전달본의 제목 기반 청크

- `solar_handoff/documents/`와 `document_evidence/`는 각각 151개이고, `chunks/draft-a-v1/chunks.jsonl`은 제목 기반 A안 1,504개다. 001·002는 역사적 문서·근거를 보존하고 003–151은 생성한다. [생성 안내](../../../solar_handoff/scripts/README.md)의 오프라인 `--check`와 기존 입력을 덮어쓰지 않는 새 출력 경로를 사용한다.
- 등록부와 원본 청크는 `pending` / `index_eligible=false`다. 별도 사용자 151문서 승인 의사는 이 상태와 구분한다. 새 입력의 변경·인덱싱 전에 정확한 입력과 사용 범위의 승인 여부를 확인한다. 과거 승인 스냅샷 검증 시스템을 재도입하지 않는다.
- 청크는 `source_document`, `heading`, `source_heading_lines`, `source_lines` 등 위치 메타데이터를 보존한다. `solar_handoff/src/citations.py`는 이를 미검증 위치로 표시하며 인용 ID 검사만으로 문서 위치나 주장별 근거 적합성을 보증하지 않는다. 근거 연결은 절·의존성 단위이며 행별 의미 정확성은 별도 검토한다.

## 입력 / 출력

- 입력: 사람이 검토하고 승인한 포켓몬별 Markdown, 근거가 되는 정제 데이터와 출처 매니페스트, 필요한 경우 검증된 상성 계산 결과.
- 파일럿 문서는 작성과 검증에 활용할 수 있지만 승인 전에는 인덱싱하지 않는다. 공유되지 않은 개인 로컬 파일을 필수 입력으로 삼지 않는다.
- 출력: `data/chunks/chunks.jsonl`(예정). 각 항목은 읽을 수 있는 청크 본문과 검색용 메타데이터를 담고, 상세 근거 연결 기록을 참조한다.
- 메타데이터의 정식 계약은 `contracts/chunk_schema.json`(예정)으로 관리한다. 아래 필드와 섹션은 초안이며 실제 구현 전 계약을 확정한다.

## 청크 단위

Markdown 문서 하나를 고정 제목 단위로 나눈다. 아래 표가 기본 경계(템플릿 tpl2·tpl3a 공통, 기각된 tpl3b도 같음)다. Solar 전달본은 제목 기반 A안을 쓰며 변경은 별도 결정·평가한다. 제목 문자열은 파일럿 문서(`data/synthetic/pilot/bulbasaur_red_blue.md`)를 따르고, 표 순서가 문서 순서다. `{포켓몬명}`은 문서 `#` 제목으로 채운다.

| Markdown 제목 | section | 내용 |
| --- | --- | --- |
| `# {포켓몬명}`부터 첫 `##` 전까지(도감번호·타입), `## 어떤 포켓몬인가요?` | profile | 이름, 도감번호, 타입, 확인된 기본 소개 |
| `## 종족치` | stats | 종족치 |
| `## 진화` | evolution | 속한 진화 계통의 모든 단계와 단계별 조건, 문서 대상의 위치 |
| `## 기술` | (상위 제목) | 아래 세 절을 묶는다 |
| `### 레벨업으로 배우는 기술` | learnset_level | 레벨업으로 배우는 기술, 습득 레벨, 기술 타입 |
| `### 기술머신·비전머신으로 배우는 기술` | learnset_machine | TM/HM으로 배우는 기술, 머신 번호, 기술 타입 |
| `### 머신은 어디서 얻나요?` | machine_acquisition | 해당 머신의 확인된 획득 장소와 방법 |
| `## 타입 · 상성` | (상위 제목) | 아래 세 절을 묶는다 |
| `### 자속 보정 (같은 타입 기술 1.5배)` | stab | 자속 설명과 근거가 확인된 예시 |
| `### 공격 상성 ({포켓몬명}과/와 같은 타입 기술이 잘 통하는 타입)` | attack_matchup | 자기 타입 기술의 단일 타입 상대 상성 |
| `### 방어 상성 (약점과 저항)` | defense_matchup | 공격받을 때 복합 타입 상성 (약점·저항·무효) |
| `## 획득처` | encounter | 해당 포켓몬을 얻는(잡는·받는) 방법: 버전별 장소·방법·레벨 (tpl3a부터 아래 '획득처 절') |

- 공격 상성 제목의 조사 `과/와`는 포켓몬명 마지막 한글 음절의 받침으로 정한다. 받침이 있으면 `과`(리자몽과), 없으면 `와`(이상해씨와·피카츄와)이며, 끝의 `♀`·`♂`는 건너뛴다(니드런♀과). 다른 조사를 쓴 제목은 표에 없는 제목으로 오류다 (생성기 `with_gwa_wa`).
- 제목은 앞뒤 공백만 지우고 문자열 그대로 비교한다. 코드 블록(```` ``` ````) 안의 `#` 줄은 제목으로 보지 않는다.
- 청크 구간은 해당 제목 줄부터 다음 청크 제목 직전까지다. 표 뒤 문단도 그 제목의 청크에 속한다 (예: 솔라빔 중복 습득 문단은 learnset_machine).
- 상위 제목은 청크를 만들지 않고 `###` 단위로 나눈다. 상위 제목과 첫 `###` 사이에 본문이 있으면 첫 `###` 청크 앞에 붙인다. 현재 양식에는 이 본문이 없다.
- 제목 줄은 청크 본문에 넣지 않고 머리말의 주제로 대신한다. 빈 줄을 뺀 모든 줄은 정확히 한 청크에 들어가야 한다.
- 표에 없는 제목(`####` 이하 포함), 빠진 제목, 중복 제목, 순서가 다른 제목, `#` 제목이 하나가 아니거나 이름·도감번호가 `pokemon.json`과 다른 문서는 오류로 처리하고 청크를 만들지 않는다. 가까운 section에 합치거나 건너뛰지 않는다.
- 생략할 수 있는 절은 `### 머신은 어디서 얻나요?` 하나다. Red·Blue 머신 기술이 0개인 포켓몬(현재 데이터 10·11·13·14·129·132번)만 생략하고, `### 기술머신·비전머신으로 배우는 기술`은 남겨 배우는 머신 기술이 없다고 쓴다. 머신 기술 유무와 이 절의 유무가 다르면 오류다.
- 진화 관계가 없는 포켓몬도 `## 진화`를 두고 진화하지 않는다고 쓴다. 획득 기록이 없는 포켓몬도 `## 획득처`를 두고 기록이 없다고만 쓴다. 기록이 없다는 것이 얻을 수 없다는 뜻은 아니다 (`encounters_red_blue.json`의 `scope_note`).
- 획득처 절. 본문은 `encounters_red_blue.json`의 Red·Blue 기록과 장소 대응표를 근거로 한다. 진화로 얻는 방법 등 그 파일에 없는 사실은 쓰지 않는다. 아래 최솟값~최댓값 규칙은 역사적 파일럿 생성기에만 적용하며, Solar의 003–151 문서는 원본 레벨 구간의 정확한 합집합을 보존한다. 001·002는 기존 문서 그대로 보존한다.
  - 순서: `요약: ` 문장 한 줄 → 표 → 장소·범위 문장 한 줄. 기록이 두 버전 모두 없으면 표 없이 요약 문장과 범위 문장(`PokéAPI의 등장·획득 기록 기준이며, 기록이 없다고 해서 얻을 수 없다는 뜻은 아닙니다.`)만 둔다. 표가 있으면 범위 문장 앞에 `장소는 한국어판 게임의 장소 이름입니다.`를 붙인다.
  - 요약 문장: `요약: {포켓몬명}을/를 얻는 방법(잡는 곳·받는 곳)과 장소입니다.` 뒤에 버전별 기록 문장. 두 버전의 문장이 같으면 `Red와 Blue 모두 …`, 다르면 `Red에서는 …. Blue에서는 ….`. 버전 문장은 방법 묶음 순서(야생 → 선물 → NPC 교환)대로 `{장소}에서 야생 포켓몬으로 만나는 / 선물로 받는 / NPC 교환으로 받는 기록이 있`고, 묶음의 장소가 3곳 이하면 `·`로 잇고 4곳 이상이면 `{n}곳`으로 쓴다(장소는 표). 야생 기록이 없는 버전은 `야생에서 만나는 기록은 없습니다`, 기록이 전혀 없는 버전은 `등장·획득 기록이 없고, 야생에서 만나는 기록도 없습니다`로 쓴다.
  - 표 머리글 `| 버전 | 장소 | 방법 | 레벨 |`, 조건 값이 있는 종만 `| 조건 |` 열을 더한다. 행 키는 (장소 식별자, method, condition 값). 버전마다 같은 키의 레벨을 최솟값~최댓값으로 합치고(같으면 숫자 하나), 두 버전의 키·레벨 범위가 같으면 `Red·Blue` 한 행, 아니면 `Red`·`Blue` 행을 따로 둔다. 행 순서는 Red 기록 순서, 그다음 Blue에만 있는 기록 순서다. 출현 확률은 싣지 않는다.
  - 방법 표기: `walk` 야생(풀숲·동굴), `old-rod`·`good-rod`·`super-rod` 야생(낡은낚싯대·좋은낚싯대·대단한낚싯대 낚시), `surf` 야생(파도타기), `static` 야생(고정 출현), `pokeflute` 야생(포켓몬 피리), `gift` 선물, `npc-trade` NPC 교환. 이 밖의 method는 오류로 멈추고 표기를 정한 뒤 쓴다. 조건 표기: `coins-{n}` 코인 {n}개, `trade-{포켓몬}` {한국어명}과/와 교환, 그 밖(예: `item-helix-fossil`)은 한국어 근거가 없어 식별자 코드 표기로 쓰고 보고한다. 방법·조건 표기는 팀 번역이며 사람 검토 대상이다.
  - 제목은 `## 획득처` 그대로 둔다 (머리말·제목 표·청크 ID를 바꾸지 않고 본문만 보강).
- 청크 본문 앞에 `{포켓몬명} — {주제}` 머리말 한 줄을 붙여 독립적으로 읽히게 한다 (본문과 출처 규칙 2). 주제는 해당 제목 문자열이며 상위 제목 경로는 붙이지 않는다 (예: `이상해씨 — 방어 상성 (약점과 저항)`). profile 주제는 `기본 정보`다. 도감번호·게임 버전은 머리말에 넣지 않고 메타데이터(`doc_id`·`chunk_id`·`pokemon_id`·`games`·`version_group`)에만 둔다. 머리말은 문서의 `#` 제목과 제목 줄에서 만들고 새 사실을 더하지 않는다.
- 상성 표준 용어: 공격 상성 절은 `효과가 굉장한(2배)`·`효과가 별로인(0.5배)`·`효과가 없는(0배)`, 방어 상성 절은 `약점`(4배·2배)·`저항`(0.5배·0.25배)·`무효`(0배)를 표 머리글·행과 `요약: `으로 시작하는 요약 문장 한 줄에 쓴다. 채택 템플릿(tpl3a)의 요약 문장은 tpl2와 같다: 공격 요약은 `요약: 효과가 굉장한(2배) 상대 타입은 {기술 타입} 기술이 …입니다. …`, 방어 요약은 `요약: {포켓몬명}의 약점은 …이고, 저항은 …이며, 무효(0배)인 타입은 …입니다.` (생성기 `attack_summary`·`defense_summary`, direction 없음). 공격 표는 세 배율 열, 방어 표는 4배·2배·0.5배·0.25배·0배 다섯 행을 고정하고 해당 타입이 없으면 `없음`으로 쓴다. 표에 없는 타입은 1배다. 요약 문장은 표에서 정해진 형식으로 만들어지며 생성기가 표·`type_chart`·`BattleRules` 계산과 대조한다. `강점` 같은 모호한 표현은 쓰지 않는다 (쿼리 리라이트에서 처리). 자속 절에는 상성 용어를 쓰지 않는다.
- 상성 요약 방향 문장 (tpl3b, **기각됨**): 공격 요약 앞에 `{포켓몬명}이/가 상대에게 {자기 타입들} 타입 기술을 쓸 때의 상성입니다.`, 방어 요약을 `{포켓몬명}이/가 공격받을 때의 상성입니다. {포켓몬명}에게 효과가 굉장한(2배 이상) 기술 타입, 즉 약점은 … {포켓몬명}을/를 상대할 때 유리한 기술 타입은 약점인 …입니다.` 형식으로 쓰는 규칙(조사 `with_eul_reul`·`with_i_ga`). 파일럿 비교에서 기각해 새 문서에 쓰지 않는다. 사유: 목표 질의(`{포켓몬}한테 효과가 굉장한 타입`, `{포켓몬}을 상대할 때 쓸 타입`) 순위 변화 없음(각 3위), 기존 질의 2개 악화(`강점` 5위→순위 밖, `잘 버티는 타입` 4→5위), Hit@5 25→24, MRR 0.765→0.755 (tpl3a 대비).
- 상성 방향(공격·방어) 구분 문제는 문서 문구가 아니라 재정렬·쿼리 리라이트·상성 계산 툴(`gen1_battle_rules.py`)이 담당한다.
- 획득처·머신 획득처의 장소는 `data/processed/location_names_ko_red_blue.json` 대응표의 `name_ko`로 쓰고, 식별자(`pallet-town-area`, `SilphCo7F` 등)는 본문에 쓰지 않고 근거 연결(`location_name:{종류}:{식별자}` 레코드)에만 둔다. `name_ko`가 `null`이면 식별자를 코드 표기로 쓰고 보고한다. 대응표는 사용자가 전체 항목을 승인했고(`review_status` approved, 홍련섬 결정 포함, 파일 `review` 메타), 영문 장소명은 보강하지 않는다.

- 원본 문서에 없는 사실을 채우지 않는다. 외형·생태를 새로 생성하거나 `flavor` 청크를 의무화하지 않는다.
- 진화 절은 직접 진화만이 아니라 대상 포켓몬이 속한 진화 계통의 모든 단계와 단계별 조건을 다룬다. 계통 전체를 한 진화 도식(`` ```text `` 블록, `── 조건 ──▶` 형식)과, 문서 대상이 어느 단계에서 무엇으로 진화하는지 또는 무엇에서 진화하는지 드러나는 설명 문장으로 쓴다. '1단계 중 1번째' 같은 번호 표기는 쓰지 않는다. 예시는 파일럿 이상해씨 문서(`data/synthetic/pilot/bulbasaur_red_blue.md`의 진화 절)다. 계통은 `evolutions_red_blue.json`의 Red·Blue 관계(`evolves_from`·`evolves_to`)로 묶는다. `evolution_chain_url`은 다른 세대 종을 거쳐 별개 계통을 합칠 수 있으므로 쓰지 않는다 (예: 시라소몬·홍수몬).
- 조건은 레벨 진화는 레벨, 아이템 진화는 돌 이름, 교환 진화는 통신 교환으로 표기한다. 돌 이름은 `evolution_items_red_blue.json`의 한국어 이름을 근거로 쓰고, 진화 청크 근거에 해당 아이템 레코드를 연결한다. 갈래 진화(예: 이브이)는 갈래마다 조건을 따로 쓰고 도식에서 갈래를 줄마다 나눈다. 갈래 끝 포켓몬 문서도 같은 계통 전체를 쓴다. Red·Blue에서 진화 관계가 없는 포켓몬은 진화하지 않는다고 쓰고 다른 세대 진화형을 병기하지 않는다.
- 데이터에 없거나 비어 있는 조건은 추측하지 않고 미확인으로 남긴다. `api_matching_details`의 다른 버전 그룹 조건을 Red·Blue 조건으로 쓰지 않는다.
- 기술 표(`learnset_level`·`learnset_machine`)에는 `pokemon.json` learnset 중 `version_group`이 `red-blue`이고 `method`가 `level-up` 또는 `machine`인 기록만 넣는다. 그 밖의 method는 Red·Blue 게임 안에서 배우는 방법이 아니므로 표와 습득 건수에서 뺀다 (예: 25번 피카츄의 `stadium-surfing-pikachu` 파도타기).
- 레벨업과 머신 목록은 확인된 범위를 표시하고, 같은 기술의 여러 습득 방법을 유지한다. 모든 경로가 검증되지 않았으면 전체 경로라고 주장하지 않는다.
- Solar A안의 긴 기술 목록·머신 획득처도 제목별 절 전체를 유지한다. 향후 분할은 별도 결정·평가하며, 분할 시 각 청크가 포켓몬명, 주제, 표 머리글과 필요한 행을 갖추게 한다.
- 포켓몬별 문서와 별도로 기술 문서를 도입하면 기술별 `move` 청크를 둘 수 있다. 문서 준비와 범위를 확인하기 전 165개 청크의 존재를 전제하지 않는다.
- Solar A안의 경계를 바꾸면 제목 표와 청크 ID·근거·평가 매핑을 함께 검토한다. 문서당 5개, 전체 약 920개 같은 고정 수치를 완료 조건으로 삼지 않는다.

## 템플릿 버전

| 템플릿 | 제목 | 머리말 | 장소 | 파일 |
| --- | --- | --- | --- | --- |
| tpl1 | `### 자속 보정`, `### 공격할 때`, `### 공격받을 때` | `{포켓몬명} (도감번호 {번호}, 영문 Red·Blue) — {상위 > 제목}` | 식별자 | `data/synthetic/pilot/v1/` (schema_version 2, 수정 금지) |
| tpl2 | 위 '청크 단위' 표 | `{포켓몬명} — {제목}` | 대응표 `name_ko` | `data/synthetic/pilot/v2/` (schema_version 3, `template_version` 키, 수정 금지) |
| tpl3a (채택, 기본) | tpl2와 같음 | tpl2와 같음 | tpl2와 같음 | `data/synthetic/pilot/v3a/` (tpl2 + '획득처 절' 보강, 다른 절은 v2와 바이트 동일, 수정 금지). 최신본 `data/synthetic/pilot/bulbasaur_red_blue.{md,json}`은 v3a의 바이트 사본 |
| tpl3b (기각) | tpl2와 같음 | tpl2와 같음 | tpl2와 같음 | `data/synthetic/pilot/v3b/` (tpl3a + 상성 요약 방향 문장, 기각된 실험 기록, 수정 금지) |

- 현재 채택 템플릿은 tpl3a다. 파일럿 비교(v2→v3a)에서 `어디서 잡아` 질의가 2→1위, Hit@1 15→16, MRR 0.747→0.765로 좋아졌고 모호 질의 `강점`은 4→5위(Hit@5 유지, 쿼리 리라이트 담당)였다.
- 생성기는 `--template tpl1|tpl2|tpl3a|tpl3b`(기본 tpl3a)로 고른다. tpl3b는 생성기의 `REJECTED_TEMPLATES`에 사유와 함께 남긴 기각된 실험이며 `--template tpl3b --check`로 명시할 때만 v3b 재현을 확인한다. 기본 템플릿·최신본으로는 고르지 않는다 (기본 템플릿이 기각 목록에 있으면 생성기가 멈춘다). tpl1·tpl2는 v1·v2 테스트 컬렉션(`test-pilot-v1-te3s-tpl1`·`test-pilot-v2-te3s-tpl2`) 재현용 기준선이며 `--template tpl1|tpl2 --check`가 기준선 JSON과 비교하고, 기준선 JSON에는 쓰지 않는다. 기준선 JSON은 생성기·매니페스트 자신의 해시와 Markdown 경로를 담고 있어 바이트 동일 재생성은 불가능하므로, 이 세 값은 비교에서 빼고 기준선 값인지 따로 확인한다(v2 JSON의 Markdown 경로는 당시 최신본 위치이며 같은 바이트의 보존본이 `v2/`에 있다). v3a·v3b JSON도 고정본이다: 생성기 sha256(파일럿 비교 당시 값, `TPL3_BASELINE`)만 비교에서 빼고 나머지는 바이트 비교하며, 생성기는 v1~v3b JSON과 최신본에 쓰지 않는다(새 출력은 `--output`). 기본 템플릿 `--check`는 최신본이 v3a 저장본의 바이트 사본인지도 확인한다. tpl3a·tpl3b 테스트는 `tests/test_pilot_chunks_v3.py`다 (tpl3b 방향 문장 검사는 기각된 실험의 재현 검사로 남긴다).
- 템플릿(제목·머리말·표 양식)이 바뀌면 청크 본문이 바뀌므로 새 `index_version`(예: `v2-te3s-tpl2`)으로 전체 빌드하고 평가한다 (`vectordb` 스킬). 이전 템플릿 컬렉션과 섞지 않는다.

## 본문과 출처 규칙

1. 임베딩 본문은 검토된 Markdown 내용을 기준으로 한다. 필요한 문맥을 덧붙이더라도 원본에 없는 게임 사실을 만들지 않는다.
2. 각 청크가 독립적으로 이해되도록 포켓몬명과 주제를 머리말에 포함한다. 도감번호와 Red·Blue 기준은 메타데이터로 연결해 답변 및 필터에서 혼동되지 않게 한다.
3. 정형 값은 해당 버전의 정제 데이터에서 대조하고, 상성·자속은 검증된 계산과 입력을 확인한다. 누락은 미확인으로 남기고, 습득하지 못하는 예시를 실제로 배운다고 쓰지 않는다.
4. 청크마다 Markdown 문서와 절·위치를 기록하고, 청크의 주장에 필요한 모든 정제 파일과 레코드 ID를 연결한다. JSON 포인터를 쓰면 실제 레코드 ID와 함께 검증한다. 계산 결과에는 입력과 계산 규칙 버전도 연결한다. 진화 청크는 계통에 등장하는 모든 진화 관계의 `evolutions_red_blue.json` 레코드와 등장 포켓몬 전원의 `pokemon.json` 레코드를 연결한다 (예: 이상해씨 문서는 두 파일의 1~3번 포켓몬 레코드).
5. 출처가 불명확하거나 확인되지 않은 설명은 승인된 근거로 취급하지 않는다. 데이터 이용·재배포 조건과 사람이 검토한 상태를 별도로 확인한다.
6. Markdown을 수정하면 파생 청크의 본문과 근거 연결을 다시 생성·검증한 뒤 동기화한다. 동일한 ID만으로 텍스트가 최신이라고 판단하지 않는다.
7. 벡터 검색과 BM25를 비교하거나 결합할 때는 동일한 승인 청크 텍스트와 ID를 사용한다. 평가셋과 정답은 검색 문서에 넣지 않는다.

## 청크 ID

- 기본형: `pokemon:{id}#{section}` (예: `pokemon:25#stats`). ID는 포켓몬과 주제를 식별하며 Markdown 줄 번호나 실행 시각에 의존하지 않는다.
- 포켓몬별 Markdown에서는 제목으로 ID를 정한다. `{id}`는 `pokemon.json`과 대조한 도감번호 정수(앞 0 없음), `{section}`은 '청크 단위' 표에서 제목에 대응하는 값이다. 파일럿 이상해씨 문서는 `pokemon:1#profile`부터 `pokemon:1#encounter`까지 10개다. 파일럿 청크 JSON(`data/synthetic/pilot/bulbasaur_red_blue.json`, schema_version 3, tpl3a — v2·v3b 판도 같은 ID)도 이 10개 ID를 쓰며, `scripts/helper/build_pilot_chunks.py`가 Markdown에서 다시 만들고 `tests/test_pilot_chunks.py`(v2 기준선)·`tests/test_pilot_chunks_v3.py`(tpl3a, 기각된 tpl3b 재현)가 재생성 결과·줄 대응·근거 포인터를 검증한다.
- 한 섹션을 여러 청크로 나누면 안정적인 항목 키를 더해 구별한다. 예: `pokemon:1#machine_acquisition:TM22`. 같은 청크 집합에서 ID는 유일해야 한다.
- 항목 ID를 만들기 어려운 분할은 구현 전에 안정적인 규칙을 정하고 계약에 기록한다. 분할 경계·의미가 바뀌면 기존 평가셋의 근거 ID도 재검증한다.
- 별도 기술 문서의 경우 `move:{id}`를 사용할 수 있다. 문서·청크 ID와 인덱스 레코드 ID의 관계는 `vectordb` 스킬을 따른다.

## 메타데이터와 근거 연결 (초안)

| 키 | 용도 |
| --- | --- |
| chunk_id, document_id | 청크와 포켓몬별 원문 식별 |
| entity, pokemon_id, move_id | 대상 구분 및 해당 ID |
| name_en, section | 이름과 청크 주제 |
| game_version | 영문 Red·Blue 기준 구분 |
| review_status | 사람의 검토·승인 상태 |
| source_loc | 원문 위치: Markdown 문서 경로와 절 (예: `data/synthetic/pilot/bulbasaur_red_blue_plain.md#종족치`). 필요하면 행 범위를 덧붙인다. 검색 결과·답변 출처·평가셋 허용 근거에서 바로 확인하는 값 |
| source_ref_id | 도감번호 3자리(`pokemon_id` zero-pad, 예: `001`). 출처 원문 조회 키: API documents 엔드포인트가 문서 폴더에서 `<번호>_*.md`(Solar 원문 `solar_handoff/documents/001_이상해씨.md`)를 찾는다 |
| type_{normal, fire, …} | 타입별 필터가 필요할 때 사용하는 불리언 |
| content_hash, meta_hash, schema_version | 변경 감지와 계약 버전 |

- `chunk_id`, `document_id`, 원문 위치는 발제 필수 항목이다. 위 `source_loc`은 일반 계약 초안이며 Solar는 별도 위치 필드에서 미검증 표시값을 만든다. Markdown 절이나 행이 바뀌면 위치도 다시 검증한다.
- `source_ref_id`는 청크 문서의 `pokemon_id`(정제 레코드 `id`)를 `f"{pokemon_id:03d}"`로 만든 값이다. 원문 Markdown 경로에 의존하지 않으며 경로는 `source_path`에 따로 둔다. `pokemon_id`가 정수가 아니거나 1~151 밖이면 조용히 넘기지 않고 실패시킨다(`scripts/helper/pilot_vector_index.py`, `tests/test_pilot_vector_index.py`).
- API가 조회하는 원문 Markdown 파일명은 `<번호 3자리>_` 접두어를 가져야 하고(예: `001_이상해씨.md`), 한 문서 폴더에 같은 번호 파일은 하나만 둔다.
- 검색 필터에 필요한 메타데이터는 스칼라 값으로 둔다. 정제 레코드·계산 근거 같은 상세 출처 연결은 청크 JSON의 `source_records`·`source_lineage`에 두며, 구체적인 저장 형식은 계약에서 확정한다.
- 타입 enum은 `types.json`의 15개 소문자 영문을 기준으로 한다. 한글명·별칭은 텍스트와 `resolve_name` 툴에서 처리한다.
- `content_hash`와 `meta_hash`는 `vectordb` 스킬의 규칙을 따른다. 청크 템플릿·섹션이나 임베딩 모델이 바뀌면 새 `index_version`으로 전체 빌드하고 평가한다.

## 검증

- 승인된 Markdown의 대상 ID·버전과 청크의 ID가 맞고, 중복·누락 없이 추적되는지 확인한다. 미확인 또는 미승인 내용은 인덱스에서 제외한다.
- 각 청크 텍스트가 해당 Markdown 구간과 일치하고, 연결된 정제 레코드 및 계산 근거가 실제 내용을 뒷받침하는지 확인한다.
- 레벨업과 TM/HM 기술·타입, 중복 습득 방법, 진화 계통의 단계·조건과 근거 레코드, 확인된 머신·포켓몬 획득처와 상성 표의 누락·변형을 검사한다.
- 섹션별 분포와 텍스트 길이, 분할된 표의 독립적 이해 가능성을 확인한다. 같은 승인 입력과 설정으로 두 번 생성하면 청크 텍스트·ID·해시가 같아야 한다.
- 계약 파일이 구현된 후 모든 청크를 스키마로 검증한다. Markdown이나 섹션 경계가 바뀌면 청크·근거·평가셋 매핑을 재검증한다.
- 청크 경계 변경은 별도 검색 품질 평가와 사용자 결정을 거친다. 인덱스 생성·검색 테스트를 실행하지 않았다면 완료로 보고하지 않는다.
