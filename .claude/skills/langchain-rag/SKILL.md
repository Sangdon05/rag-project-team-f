# langchain-rag

현재 Solar 질문 CLI·대화 서비스와 향후 LangChain 질의응답 에이전트 체인·프롬프트를 다룬다.

## 현재 Solar handoff

### 질문 CLI와 공통 검색 정책

- `solar_handoff/src/cli.py`는 한 질문의 검색·답변을 수행해 JSON 트레이스를 출력한다. 과거 `dev_rag`와 별개이며, 대화 도구 선택이나 형제 청크 확장을 적용하지 않는다. `retrieval.py`, `providers.py`, `citations.py` 및 `solar_handoff/config/retrieval.json`이 각각 검색, 모델 호출, 출처와 고정 검색 설정을 담당한다.
- 검색 경로는 원질문을 보존하고 선택적 GPT rewrite를 적용한 검색어를 Solar query API로 임베딩한다. A는 벡터 후보 최대 20개에서 상위 5개를 선택한다. B는 벡터와 BM25 각각 최대 20개를 RRF(k=60)로 결합해 상위 5개를 선택한다. C는 B의 상위 정확히 5개를 원질문 기준 GPT로 재순위화하며 5개 미만이면 실패한다. 답변은 GPT 전용이다.
- rewrite의 완료된 응답이 거절 또는 형식 오류인 경우에만 재작성 전 검색어로 되돌린다. 네트워크 등 결과가 불명인 실패는 fallback하지 않고 실패 처리하며 자동 재시도하지 않는다. 유효한 rewrite도 의미 보존은 미검토다.
- 출처 검사는 인용 ID가 선택된 청크에 속하는지와 형식을 확인한다. path·heading·불연속 줄 범위는 메타데이터 표시이며, 실제 문서 위치와 주장에 대한 근거 적합성은 사람이 대조해야 한다. CLI의 `status`·`answer`와 `[[chunk ID]]` 인용 계약은 대화 전용 형식과 별개다.
- 검색은 루트 환경의 `DATABASE_URL`, `UPSTAGE_API_KEY`, `UPSTAGE_EMBEDDING_MODEL`, `UPSTAGE_QUERY_MODEL`을 사용한다. GPT 도구 선택·답변·rewrite·C는 `OPENAI_CHAT_MODEL`, `OPENAI_API_KEY`를 사용한다. 설정과 응답의 모델 ID 모두 `gpt-` 접두사여야 하나 정확한 일치는 요구하지 않는다 (alias가 날짜가 붙은 revision으로 응답할 수 있음). 별도 승인된 DB 접근·비용 확인 후에만 실제 호출하며 CLI에는 `--allow-cost`가 필요하다. 환경과 안전 경계는 [Solar 전달본](../../../solar_handoff/README.md)을 따른다.
- 확인된 실제 질문은 Solar + C + rewrite + GPT 1건뿐이다 (`solar_handoff/README.md`의 확인된 실 실행 범위). `pokemon:133#profile`의 이브이 노말 타입은 `solar_handoff/documents/133_이브이.md` 6·10행과 대조됐다. 다른 조합의 성공이나 운영 준비를 뜻하지 않는다.

### 대화 서비스: 단일 도구 선택과 근거 전달

- `solar_handoff/src/conversation.py`는 전체 대화와 마지막 사용자 질문을 GPT에 보내 [네 Responses 도구](../tool-calling/SKILL.md) 중 하나를 선택하게 한다. 서버가 검증된 호출 하나만 실행한다. 별도 질문 라우터나 LangChain 에이전트가 아니다.
- 무인수 `search_pokedex`는 원질문과 길이 한도에 맞는 최근 사용자 질문으로 검색어를 만들고 위 A/B/C·선택적 rewrite 정책을 그대로 사용한다(`SOLAR_RETRIEVAL_METHOD` 기본 B, `SOLAR_REWRITE` 기본 `false`). 답변 근거는 검색 결과를 보존하고 같은 문서의 형제 청크를 더하되 총 50개·직렬화 UTF-8 96,000바이트 한도를 적용한다. 일반 검색의 답변 생성, 재작성·C 재순위화는 도구 선택과 별도 호출이다.
- 일반 검색 답변에는 원질문·전체 대화·선택 근거를 보낸다. 대화 전용 strict 응답은 `status`와 `claims`로 구성하며, 각 주장에는 `text`와 `source_ids`를 요구한다. `source_ids` 후보는 이번 요청의 선택 청크 ID뿐이다. 서버도 블록과 참조를 재검사하고 인용된 청크의 본문 첫 등장 순서로 `[n]`과 중복 없는 `sources`를 만든다. 인라인 인용 표기를 추정·보정하지 않는다. `insufficient_evidence`는 검증을 통과한 주장만 고정 안내와 함께 표시하거나 안내만 반환한다.
- 팀·기술 답변은 기존 도구 계산 결과와 검증된 정확한 청크를 서버가 연결한다. 도구 선택 GPT 1회 외에 후속 GPT·질의 임베딩·BM25·벡터 검색·재작성·재순위화를 하지 않는다. 필수 근거가 없으면 결과 대신 안전 안내를 반환한다. 확인 질문과 포켓몬 근거가 필요 없는 기술 답변(변화기·별도 피해·미확정 분류·약점 대상 0건 등)은 DB를 열지 않는다. 기술 분류의 `move:{id}` 정제 레코드는 본문에만 표시한다.
- 일반 검색의 완성된 모델 답변에서 인용만 거부되면 모든 주장을 버린다. HTTP 200 `mode=rag`, 고정 한국어 안내, 빈 `sources`를 반환하고 실제 사용이 확인된 `embedding`은 유지한다. 공급자·DB·일반 유효성 오류는 기존 502이며 재시도하지 않는다. 인용 거부 경고는 공급자 원문이나 원본 예외 없이 [Solar 전달본](../../../solar_handoff/README.md)의 고정 사유만 기록한다. HTTP 계약은 [API–RAG 연결 가이드](../../../docs/references/api-rag-integration.md)가 원본이다. 대화 감사 로그는 정상 답변의 도구, 호출 수, 선택·인용 근거 ID 등 메타데이터이며 아래의 향후 평가 JSONL과 별개다.
- 새 대화 경로의 확인 범위는 [Solar 전달본의 오프라인 검증](../../../solar_handoff/README.md)까지다. 기존 청크·인덱스·모델 설정은 유지했고 재임베딩하지 않았다. 실제 GPT·Solar·DB 실행이나 공식 평가를 추가로 수행하지 않았다.

## 향후 에이전트 구성 (구현 예정)

- LangChain tool-calling 에이전트 1개 + `tool-calling` 스킬의 향후 툴 8개를 설계한다. 별도 라우터 체인은 두지 않는다. 그 설계의 인수 있는 `search_pokedex`는 현재 Solar 대화의 무인수 계약과 다르다.
- 권장 흐름: 특정 포켓몬·기술 질문 → `resolve_name` → `get_*` 또는 `search_pokedex(pokemon_id=…)`. 상성 질문 → `type_effectiveness`.
- 정형 조회에 쓰는 실제 정제 파일과 미확인 처리 기준은 `tool-calling` 스킬을 따른다. `pokedex_extra.json`의 존재를 전제하지 않는다.
- 상성 툴 결과의 지원 상태·배율과 기술 습득 여부는 `tool-calling` 스킬의 상성 계산 계약에 따라 구분한다.
- 향후 에이전트의 검색 방식, k, 필터, MMR과 후보 결합·재정렬 설정은 이 스킬 소유다. 현재 Solar 검색 설정은 별도 경로에서 config 값을 코드의 기대값과 대조한다.

## 향후 에이전트 검색 방식 비교 (구현 예정)

| 실험 | 검색 과정 |
| --- | --- |
| A | 벡터 검색 |
| B | BM25 키워드 검색과 벡터 검색의 후보 결합 |
| C | B와 같은 방식으로 후보를 결합한 뒤 재정렬 |

- 세 방식은 선택 가능한 설정으로 준비한다. 이것은 별도 질문 라우터가 아니라 `search_pokedex`의 검색 설정이다.
- 벡터와 BM25는 동일한 승인 청크 텍스트·ID와 버전을 사용한다. 미승인 문서를 인덱싱하지 않는다.
- B와 C 비교에서는 후보 생성 설정과 후보 풀을 같게 하고 재정렬 유무만 바꾼다. 최종 반환 k를 같게 하되, 재정렬 전 후보 수는 별도 설정·기록한다.
- 후보 결합 방식, 점수 처리, BM25 토큰화·필터, 임베딩·재정렬 모델과 버전, 후보 수·최종 k는 config 및 실행 기록에 명시한다. 서로 다른 점수의 크기가 같다고 가정해 무조건 더하지 않는다.
- 정형 조회·계산 툴은 그대로 유지한다. 검색 결과만 비교하는 실험과 툴을 포함한 전체 답변 실험은 구분해 기록한다. 검색을 쓰지 않은 질문에 검색 결과를 만들어 넣지 않는다.
- 설정·검색기·인덱스·청크와 평가 데이터는 아직 구현된 것으로 가정하지 않는다. 부족하면 `blocked`와 선행 조건을 보고한다.

## 향후 에이전트 시스템 프롬프트 규칙

1. 툴 결과에 있는 내용으로만 답한다.
2. 근거 있는 답에 출처(`pokemon_id` / `move_id` / `chunk_id`)를 붙이고, 해당 ID에서 문서 위치와 정제 데이터·계산 근거를 확인할 수 있게 한다. 확인 불가한 근거는 만들어 내지 않는다.
3. 영문 Red·Blue 기준으로 답한다. 다른 세대의 값을 함께 표시하지 않으며, 다른 세대에 관한 요청은 지원 범위 밖으로 안내한다.
4. 근거가 없거나 범위(1~151번) 밖이면 모른다고 답한다.
5. 수치는 정규화 단위(m, kg) 그대로 쓴다.

검색 결과의 청크 ID와 문서·원본 근거 연결은 `chunking` 스킬과 확정된 청크 계약을 따른다.

## 향후 에이전트 실험 재현성

- LLM `OPENAI_CHAT_MODEL`(= `gpt-6-luna`), temperature 0을 목표로 한다. 모델명은 환경 변수로 읽고 실행 기록에 남긴다. 현재 Solar GPT 호출은 temperature를 지정하지 않는다.
- 비교 시 같은 승인 문서·청크 버전, 질문 집합, 답변 모델·프롬프트, 툴 설정과 최종 k를 고정하고 변경한 검색 조건을 기록한다.
- 개발셋에서 설정을 정한 뒤 최종 평가 전 설정과 평가셋을 고정한다. 평가 정답은 검색 문서·프롬프트에 넣지 않는다.
- 실행마다 검색 방식, config 스냅샷 해시, 청크·`index_version`, 답변·임베딩·재정렬 모델 버전과 해당 설정을 기록한다. 해당하지 않는 모델은 명시적으로 제외한다.
- 질문별 검색·답변 시간과 사용 가능한 토큰·비용 정보를 기록한다. 측정할 수 없는 값은 알 수 없음으로 남긴다.

## 향후 에이전트 트레이스 로깅 계약 (구현 예정)

질문마다 JSONL 한 줄. Eval의 실패 분석이 이 로그에 의존한다. 아래는 구현 계약을 정하기 위한 예시이지 실제 실행 결과가 아니다.

```json
{"qid": "...", "question": "...", "index_version": "...", "config_hash": "...",
 "retrieval": {"method": "A", "called": false, "pre_rerank": null, "final": null, "latency_ms": null},
 "tool_calls": [], "answer": "...", "citations": [], "latency_ms": null, "tokens": null}
```

- `method`는 선택된 A/B/C 설정이다. `called: false`는 검색 미호출로 후보와 시간은 `null`이다. `called: true`인데 결과가 없으면 `final: []`로 구별한다.
- `pre_rerank`와 `final`에는 후보의 청크 ID·순위·사용 가능한 점수와 출처 연결을 기록한다. B와 C의 공통 결합 후보를 추적하고 A에서 해당하지 않는 재정렬 전 목록은 `null`로 표시한다.

## 향후 에이전트 검증 계획

- 질문 유형별 1개 이상 실행: 단일 사실, 기술/습득, 상성, 비교, 집계, 서술형, 범위 밖
- 세 검색 설정이 같은 청크 집합에서 작동하고 B·C의 후보 생성 조건이 일치하는지 검증한다. 빈 결과, 중복 청크·출처 연결, 재정렬 전후 순위와 설정 변경도 테스트한다.
- 답변 가능한 주장에 출처를 붙이고 근거가 부족하면 출처를 꾸미지 않고 확인 불가를 안내한다. 트레이스 생성과 검색을 쓰지 않은 경우의 기록을 확인한다.
- 같은 질문별로 검색된 근거와 답변 결과를 분리해 독립 평가에 넘긴다. 평가자는 질문별 허용 근거 청크 ID와 검색 순위를 대조하고, 별도로 답변의 정확성·근거를 평가한다. 검색 품질·답변 품질 및 실험 채택 판정은 구현자가 하지 않는다 (Eval·오케스트레이터 담당).
