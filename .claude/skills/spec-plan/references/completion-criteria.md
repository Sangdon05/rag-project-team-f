# 완료 기준 규칙

스펙 6절 완료 기준(AC)을 쓰는 규칙과, 계획 9절에서 완료를 판정하는 규칙이다. 검사 스크립트가 강제하는 항목은 (검사)로 표시한다.

## 작성 규칙

1. **결과를 쓴다.** "X 함수를 만든다"가 아니라 "`contracts/chunk_schema.json`이 있고 필수 키 N개를 정의한다"처럼 관찰 가능한 결과를 쓴다. 세부 값은 해당 원본(스킬·설계안)을 따르고 여기서 새로 정하지 않는다. 방법은 계획이 정한다.
2. **확인 방법은 셋 중 하나다.** (검사)
   - `명령: <실행할 명령>` — 누가 다시 실행해도 같은 결과가 나와야 한다. 테스트, 검사 스크립트, 개수 세기.
   - `파일: <경로>` — 파일이 있고 기대 결과에 적은 조건(필드, 행 수, 절)을 만족한다.
   - `사람: 사용자 | 팀원` — 에이전트가 판정할 수 없는 것만. 품질 판단, 평가셋 채점, 디자인 확인.
   - `보고: <에이전트>` — 읽기 전용 에이전트의 판정(예: api-reviewer APPROVE, security-reviewer 분류). 판정 원문 요약을 계획 7절에 남기고 그 행을 근거로 쓴다.
3. **기대 결과는 값이나 조건이다.** `exit 0`, `ERROR 0`, `151개`, `5개 필드 모두 존재`, `사용자가 승인`. "적절히", "충분히", "잘", "깔끔하게", "가능한 한", "최대한"은 판정할 수 없으므로 쓰지 않는다. (검사: WARN)
4. **추적성.** 모든 AC는 REQ를 하나 이상 가리키고, 모든 필수 REQ는 AC가 하나 이상 있다. (검사) 선택 REQ에 AC가 없으면 이번 작업에서 판정하지 않는다는 뜻이다.
5. **영역 게이트를 포함한다.** 바뀌는 영역의 기존 게이트를 AC로 넣는다. 값은 복사하지 않고 원본을 가리킨다.

   | 바뀌는 것 | AC로 넣을 게이트 (원본) |
   | --- | --- |
   | 모든 작업 | doc-sync `--strict` ERROR 0 ([doc-sync](../../doc-sync/SKILL.md)) |
   | 코드·설정·`.claude/` | security-check ERROR 0 ([security-check](../../security-check/SKILL.md)) |
   | `data/` | `AGENTS.md` 개발 루프 데이터·인덱스 게이트 |
   | RAG 툴·체인 | `AGENTS.md` 개발 루프 툴·체인 게이트, 평가 게이트 |
   | `api/` | [api-invariants](../../api-invariants/SKILL.md) 완료 게이트, api-reviewer APPROVE |

6. **확인자는 수행자가 아니다.** 계획에서 AC를 맡은 담당(에이전트·오케스트레이터)의 이름이 확인자 칸에 들어가면 안 된다. "api-implementer (보고 기준)"처럼 덧붙여도 같다. (검사) 오케스트레이터가 evidence 명령을 다시 실행하거나, 독립 에이전트(리뷰어, eval)나 사람이 확인한다. 예외 두 가지: `사람:` AC를 맡은 사용자·팀원은 자기 판단을 확인할 수 있고, `명령:` AC는 오케스트레이터(디렉터)가 자기 작업이어도 명령을 다시 실행해 확인할 수 있다(결과가 결정적이므로).
7. **한 AC는 한 번에 판정된다.** 여러 조건을 묶으면 하나만 실패해도 원인을 찾기 어렵다. 조건이 독립적이면 AC를 나눈다. 예외: 5번의 영역 게이트는 원본이 정한 명령 묶음을 AC 하나로 둔다. 확인 방법은 `명령: <스킬> <절> 게이트`, 근거에는 명령마다 결과를 적는다.
8. **평가셋 정답을 기대 결과에 쓰지 않는다.** RAG 품질 AC는 "eval 실행 기록 `results/{run_id}/`가 있고 지표 X가 기준 run 대비 회귀 없음"처럼 평가 절차를 가리킨다.

## 계획의 작업 완료 기준

- 작업의 `완료 기준` 칸에는 맡는 AC ID를 쓴다. 여러 작업이 한 AC를 나눠 맡을 수 있다.
- AC에 직접 대응하지 않는 지원 작업(예: 환경 준비, 설계안 작성)은 `지원: <확인 조건>`으로 쓴다. 확인 조건도 작성 규칙 2·3을 따른다.
- 스펙의 모든 AC를 맡는 작업이 있어야 계획을 승인할 수 있다. (검사)

## 판정 규칙

계획 9절에 AC마다 결과·근거·확인자를 적는다.

| 결과 | 조건 |
| --- | --- |
| `pass` | 근거(명령과 출력 요약, 경로, 커밋)를 적고, 확인자가 직접 확인했다 |
| `fail` | 기준 미충족. 수정 작업을 계획에 추가하거나 스펙을 다시 협의한다 |
| `waived` | 사용자가 이번 범위에서 빼기로 결정했다. 근거 칸에 결정자와 날짜를 적는다 (예: `사용자 결정 2026-11-26: 다음 작업으로 미룸`) |

완료 처리(`archive`) 조건. 하나라도 어기면 명령이 거부한다. (검사)

1. 스펙이 `approved` 상태로 승인 정보가 있다.
2. 연결된 활성 계획이 모두 승인 정보를 가지고, 모든 작업이 `done` 또는 `cancelled`다.
3. 스펙의 모든 AC가 완료 판정 표에서 `pass` 또는 `waived`이고 근거·확인자가 있다. 작업을 취소해도 그 AC는 빠지지 않는다 — 빼려면 `waived` 결정을 받는다.
4. 완료된 계획이 하나 이상 있다.

부분 완료는 없다. 일부만 끝났으면 남은 AC를 `waived`로 사용자 결정을 받거나(AC는 스펙의 일부이므로 HITL), 끝날 때까지 활성으로 둔다. 완료 판정과 보관 자체는 디렉터가 조건을 확인해 진행하며 사용자 확인을 기다리지 않는다.
