# spec-plan

오케스트레이터(디렉터)가 업무를 발주하기 전에 스펙을 쓰고, 사용자와 모호한 점을 해결해 승인받고, 계획을 세워 발주·검증한 뒤, 완료 기준을 충족하면 문서를 보관하는 절차다.

**사람의 판단(HITL)이 필요한 것은 스펙뿐이다.** 스펙의 문의 해결·승인·변경·취소, 완료 기준 면제(`waived`)는 사용자가 정한다. 계획 작성·승인·변경, 발주, 막힌 작업 처리, 계획 취소, 완료 판정과 보관은 오케스트레이터(디렉터)가 스펙 범위 안에서 판단해 진행하고 결과를 보고한다.
문서 상태의 원본은 각 문서의 frontmatter다. **인덱스 파일(`README.md`, `index.md` 등)은 만들지 않는다.** 끝난 문서를 보관 폴더로 옮기는 이유가 이것이다: 활성 폴더에는 진행 중인 문서만 남으므로 폴더 자체가 목록이 되고, 목록 파일을 따로 갱신할 필요가 없다. 목록이 필요하면 `workdocs.py list`로 출력만 한다.

구성:

- [templates/spec.md](templates/spec.md), [templates/plan.md](templates/plan.md) — 문서 형식 (`new` 명령이 복사)
- [references/completion-criteria.md](references/completion-criteria.md) — 완료 기준 작성·판정 규칙
- `scripts/workdocs.py` — 생성, 검사, 병렬 단계 계산, 승인, 보관, 목록 출력 (stdlib만 사용)

## 언제 쓰는가

- 작업이 에이전트 둘 이상, 또는 PR 하나 이상에 걸칠 때
- 요청에 범위·완료 조건이 모호한 부분이 있을 때
- 한 에이전트에 한 번 발주로 끝나는 작은 작업(오타, 표 한 줄)은 `AGENTS.md` 발주 양식만 쓰고 이 스킬을 쓰지 않는다

## 저장 위치와 이름

| 문서 | 활성 | 보관 |
| --- | --- | --- |
| 스펙 | `docs/specs/` | `docs/archives/specs/` |
| 계획 | `docs/plans/` | `docs/archives/plans/` |

- 파일 이름: `YYYY-MM-DD-{기능명 또는 작업명}.md`. 날짜는 작성일(`created`), 이름은 영문 소문자·숫자 kebab-case다 (예: `2026-11-26-chunk-schema-contract.md`).
- 스펙과 그 계획은 같은 이름을 써도 된다. 날짜는 각자의 작성일이다.
- 활성 폴더에는 진행 중인 문서만, 보관 폴더에는 `done`·`cancelled` 문서만 둔다. 인덱스 파일과 하위 폴더는 두지 않는다. 검사가 강제한다.
- 진행 중 목록: `workdocs.py list`, 보관 목록: `workdocs.py list --archived`. 결과를 파일로 저장하지 않는다.
- 보관 문서는 오케스트레이터가 고치지 않는다(사람은 고칠 수 있다). 다시 할 일이 생기면 새 스펙을 쓰고 `related`에 옛 id를 적는다.

## frontmatter

공통 필드 (값이 없으면 키만 두고 비운다):

| 필드 | 값 | 설명 |
| --- | --- | --- |
| `type` | `spec` \| `plan` | 문서 종류. 폴더와 맞아야 한다 |
| `id` | 파일 이름에서 `.md`를 뺀 값 | 문서끼리는 경로가 아니라 id로 가리킨다 (보관해도 안 바뀜). 종류 안에서 유일하다 |
| `title` | 한 줄 제목 | |
| `status` | 아래 상태 표 | |
| `owner` | `orchestrator` | 작성·관리 책임자 |
| `created`, `updated` | `YYYY-MM-DD` | 명령이 `updated`를 갱신한다. 손으로 고쳤을 때 갱신은 권장(검사하지 않음) |
| `approved_by`, `approved_at` | 승인자, 날짜 | 스펙은 사용자, 계획은 오케스트레이터(디렉터). `approve` 명령이 채운다 |
| `completed_at`, `archived_at` | 날짜 | `archive`·`cancel` 명령이 채운다 |
| `cancel_reason` | 한 줄 | `cancel` 명령이 추가한다 |

스펙 전용: `related` (관련 문서 id 목록). 계획 전용: `spec` (스펙 id, 필수), `base_commit` (작성 시점 main 커밋).
스펙 하나에 계획이 여럿일 수 있다. 연결은 계획의 `spec` 필드 한 곳에만 쓴다.

### 상태

| 문서 | 상태 흐름 | 뜻 |
| --- | --- | --- |
| 스펙 | `draft` → `clarifying` → `approved` → `done` | 작성 중 → 사용자와 문의 해결 중 → 사용자 승인 → 완료 기준 충족 |
| 계획 | `draft` → `approved` → `in_progress` → `done` | 작성 중 → 디렉터 확정 → 발주 시작(`start`) → 모든 작업·완료 기준 충족 |
| 공통 | 어느 단계에서든 → `cancelled` | 스펙은 사용자, 계획은 디렉터가 중단을 결정. 사유를 남기고 보관 |

## 규칙의 강도

이 스킬의 규칙은 작업 관행이지 잠금이 아니다. 사람(사용자·팀원)은 스펙·계획·보관 문서를 직접 고칠 수 있다.

- 명령(`approve`, `archive`)은 오케스트레이터가 절차를 건너뛰지 않도록 조건을 확인하고, 조건이 안 맞으면 거부한다.
- `check`는 구조(이름, 위치, 필드, 연결, 표 머리글)를 확인한다. 사람이 고친 내용 자체는 막지 않는다.
- 승인된 스펙을 사람이 고치면 그대로 따른다. 오케스트레이터가 스펙 범위·요구사항·완료 기준을 바꿔야 한다고 판단하면 사용자에게 확인한다.

## 문서 형식

스펙 ([templates/spec.md](templates/spec.md)). 최종본은 1~6절만 남는다:

| 절 | 내용 |
| --- | --- |
| 1. 배경과 목적 | 왜 하는가 |
| 2. 범위 | 포함·제외 |
| 3. 요구사항 | `REQ-n`, 결과로 쓴다. 구분 `필수`·`선택` |
| 4. 제약 | 바꾸면 안 되는 것, 따를 가드레일·스킬 규칙 (링크) |
| 5. 입력과 산출물 | 경로 + 버전(schema_version, index_version, 커밋) |
| 6. 완료 기준 | `AC-n`, 확인 방법·기대 결과·대응 REQ |
| 문의 (임시) | 승인 전에만 있다. `### Q-n. 제목` 블록마다 배경·선택지·의견·상태. 승인 전에 지운다 |

계획 ([templates/plan.md](templates/plan.md)):

| 절 | 내용 |
| --- | --- |
| 1. 개요 | 스펙 링크, 목표, 기준 커밋 |
| 2. 작업 분해 | `T-n` 표: 작업, 담당, 선행, 산출물, 완료 기준(AC-n), 상태 |
| 3. 병렬 실행 | `waves` 명령 출력. 같은 단계 작업은 동시 발주 가능 |
| 4. 발주서 | 작업마다 `AGENTS.md` 발주 양식 |
| 5. 검증과 보고 | 에이전트 보고 형식, 오케스트레이터 검토 절차, 사용자 보고 형식 |
| 6. 위험과 대응 | |
| 7. 진행 기록 | 날짜·작업·내용·근거(명령, 경로, 커밋) |
| 8. 결정 기록 | 디렉터의 판단: 계획 확정, 작업 추가·변경·취소, 막힌 작업 처리 |
| 9. 완료 판정 | AC마다 결과(`pass`/`fail`/`waived`)·근거·확인자 |

표의 머리글(`| ID | 요구사항`, `| ID | 기준`, `| ID | 작업`, `| AC | 결과`)과 문의 블록 형식(`## 문의`, `### Q-n.`, `- 상태:`, `- 의견:`)은 스크립트가 읽는 열쇠다. 열 이름과 순서를 바꾸지 않는다.

## 절차

명령은 저장소 루트에서 `uv run python .claude/skills/spec-plan/scripts/workdocs.py <명령>`으로 실행한다. 아래에서는 `workdocs.py`로 줄인다.

### 1. 스펙 작성 (오케스트레이터)

1. `git fetch` 후 관련 파일·스킬·기존 스펙을 읽는다. 보관 폴더에서 같은 주제의 옛 스펙을 찾아 `related`에 적는다.
2. `workdocs.py new spec <name> --title "..."`로 만들고 1~6절을 채운다. 완료 기준은 [completion-criteria](references/completion-criteria.md)를 따른다.
3. 저장소로 확정할 수 없는 것은 추측하지 않고 질문으로 뽑는다. 질문마다 배경, 선택지, 추천을 붙인다.

### 2. 문의 해결 (HITL)

질문 수에 따라 묻는 곳이 다르다.

| 질문 수 | 묻는 곳 | 문서 |
| --- | --- | --- |
| 3개 이하 | 채팅으로 한 번에 묻는다 | `## 문의` 절을 지운다. 답은 바로 1~6절에 반영한다 |
| 4개 이상 | 스펙 문서 `## 문의` 절에 남기고 사용자에게 `의견:` 작성을 부탁한다 | 채팅에는 문서 경로와 질문 수·제목만 알린다 |

문서로 묻는 경우:

1. `status: clarifying`으로 바꾸고 `### Q-n. 제목` 블록을 쓴다 (`- 배경:`, `- 선택지:`, `- 의견:`, `- 상태: open`). 서로 의존하는 질문은 순서를 표시한다.
2. 사용자가 의견을 쓰면 `workdocs.py questions <spec-id>`로 의견이 달린 것과 빈 것을 확인한다.
3. 의견을 읽고 반영할 수 있으면 `- 상태: resolved`로 바꾼다. 의견이 새 질문을 낳거나 불명확하면 해당 블록에 `- 후속:`을 덧붙이거나 새 `Q-n`을 추가하고 다시 부탁한다.
4. 모든 문의가 `resolved`가 되면 **최종본으로 정리한다**: 답을 1~6절 본문에 반영하고 `## 문의` 절을 통째로 지운다. 문의·의견 이력은 남기지 않는다(필요하면 git 기록에 있다).
5. 사용자가 최종본을 확인하면 `workdocs.py approve spec <spec-id> --by <사용자>`로 승인한다. `## 문의` 절, 빈 확인 방법, 완료 기준 없는 필수 요구사항, 남은 `{{...}}`가 있으면 명령이 거부하고 파일을 되돌린다. `--by`에 에이전트·오케스트레이터·디렉터는 쓸 수 없다.

사용자의 명시적 확인 없이 승인하지 않는다. 기본값으로 진행해도 된다고 사용자가 말한 질문만 추천값으로 반영한다.

승인 뒤 스펙을 바꿔야 하면: 사용자가 직접 고치거나, 오케스트레이터가 `clarifying`으로 되돌리고 같은 문의 절차를 밟은 뒤 다시 승인받는다.

### 3. 계획 작성 (디렉터 판단, 사용자 확인 없음)

1. `workdocs.py new plan <name> --spec <spec-id> --title "..."`. 스펙이 `approved`가 아니면 만들지 않는다.
2. 2절 작업 분해: 작업 하나 = 담당 하나 = 발주 하나. 읽기 전용 에이전트(frontmatter `tools`에 Write·Edit 없음)는 산출물 칸을 비워도 된다. 담당은 `.claude/agents/`의 에이전트 또는 `오케스트레이터`·`디렉터`·`팀원`·`사용자`다. 평가셋 작성·잠금처럼 사람만 하는 일은 `팀원`에게 둔다 (`AGENTS.md` 가드레일).
3. 스펙의 모든 AC를 맡는 작업이 있어야 한다. 수정한 에이전트와 그 결과를 판정하는 담당을 같은 작업에 두지 않는다 (예: 구현 T-2 → 리뷰 T-3).
4. `workdocs.py waves <plan-id>`로 단계를 계산해 3절에 붙인다. 같은 단계 작업의 산출물 경로가 겹치면 ERROR다 — 선행 관계를 넣어 순서를 정한다.
5. 4절 발주서와 5절 보고 형식을 쓴다. `done_when`은 해당 AC의 확인 방법·기대 결과를 그대로 옮긴다.
6. 디렉터가 검사(`workdocs.py check`)를 통과시킨 뒤 `workdocs.py approve plan <plan-id>`로 확정한다(`--by` 기본값 `오케스트레이터`, 하위 에이전트 이름은 거부). 사용자에게는 계획 요약을 보고만 한다.
7. 확정 뒤 작업을 추가·변경·취소하면 8절에 이유를 남기고 진행한다. 그 변경이 스펙 범위·요구사항·완료 기준을 바꾸면 2절(HITL)을 먼저 밟는다.

### 4. 실행과 기록

1. 발주를 시작하면 `workdocs.py start <plan-id>`로 계획을 `in_progress`로 바꾼다. 단계 순서대로 발주하고, 같은 단계 작업은 동시에 발주한다.
2. 보고를 받으면 `AGENTS.md` 보고 검토 절차대로 evidence를 직접 다시 실행하고, 작업 상태와 7절 진행 기록을 갱신한다. 보고 내용만으로 `done`을 적지 않는다.
3. 막히면 작업을 `blocked`로 두고 디렉터가 처리를 정한다(재발주, 작업 분할·추가, 담당 변경, 계획 취소 후 새 계획). 판단은 8절 결정 기록에 남긴다. 스펙의 범위·요구사항·완료 기준을 바꿔야 할 때만 사용자에게 묻는다 (2절 절차).
4. 커밋 전마다 `workdocs.py check`를 실행한다.

### 5. 완료 판정과 보관

1. 9절 완료 판정 표를 채운다. 스펙의 모든 AC를 판정한다(취소한 작업의 AC 포함). 확인자 규칙은 [completion-criteria](references/completion-criteria.md) 6번이다.
2. `workdocs.py archive <spec-id> --dry-run`으로 조건을 확인한다. 조건은 [completion-criteria 판정 규칙](references/completion-criteria.md#판정-규칙)이다.
3. 통과하면 `workdocs.py archive <spec-id>`. 스펙과 연결된 활성 계획을 함께 `done`으로 바꾸고(`completed_at`, `archived_at`, `updated`), 보관 폴더로 옮기고(추적 중인 파일은 `git mv`, 아직 추적되지 않은 파일은 이동), 저장소 Markdown에서 옮긴 문서를 가리키던 상대 링크를 갱신한다.
4. 5절 사용자 보고 형식으로 완료를 보고한다.

중단: `workdocs.py cancel spec|plan <id> --reason "..."`.
- 스펙 취소는 사용자 결정이다. 사유에 결정자를 적는다. 연결된 활성 계획도 함께 취소·보관한다.
- 계획 취소는 디렉터가 판단한다. 스펙은 남고 새 계획을 쓴다.

## 검사

```bash
uv run python .claude/skills/spec-plan/scripts/workdocs.py check            # 커밋 전
uv run python .claude/skills/spec-plan/scripts/workdocs.py check --strict   # PR 전 (WARN도 실패)
```

| 종류 | 뜻 |
| --- | --- |
| name, location | 파일 이름 형식, 폴더와 type·status 불일치 |
| frontmatter, approval, template | 필드 누락·형식, 승인 정보 없음, 승인 후 자리표시 남음 |
| spec, ac | REQ↔AC 연결 누락, 확인 방법 형식, 승인 뒤 남은 문의 절(WARN), 모호한 표현(WARN) |
| plan | 없는 스펙·담당·선행·AC, 순환, 같은 단계 산출물 충돌, AC 누락 |
| done | 완료 처리 조건 미충족 |
| index | 스펙·계획 폴더에 인덱스 파일(`README.md`, `index.md`)이나 하위 폴더가 있음 → 지운다 |

보관 문서에는 WARN을 내지 않는다. 출력 끝의 `루트`가 저장소 경로인지 확인한다(`WORKDOCS_ROOT`는 테스트용).

문서 링크는 [doc-sync](../doc-sync/SKILL.md)가 따로 검사한다. 스펙·계획 폴더는 허브 링크가 없으므로 doc-sync 고아 문서 검사에서 빠진다(`doc-map.json`의 `orphan_exclude`). 대신 이 검사가 폴더의 문서를 모두 확인한다.

## 하지 않는 것

- 사용자 확인 없이 스펙을 승인·변경·취소하거나, 사용자가 답하지 않은 문의를 임의로 `resolved` 처리하지 않는다.
- 문의 이력을 최종 스펙에 남기지 않는다. 승인 전에 본문에 반영하고 `## 문의` 절을 지운다.
- 반대로 계획·발주·작업 처리를 사용자 확인 대기로 멈추지 않는다. 디렉터가 정하고 보고한다.
- 완료 기준을 통과시키려고 오케스트레이터가 승인된 AC를 바꾸거나 지우지 않는다. 바꿔야 하면 사용자에게 확인한다.
- 평가셋 정답이나 `eval/` 내용을 스펙·계획에 옮겨 적지 않는다 (`AGENTS.md` 가드레일).
- 스펙·계획 목록 파일(README, index)을 만들지 않는다. 다른 문서에서 스펙·계획 폴더를 가리킬 때는 링크 대신 인라인 코드(`docs/specs/`)로 쓴다.
- 세부 절차를 스펙·계획에 복사하지 않는다. 해당 스킬·`AGENTS.md`로 링크한다.
